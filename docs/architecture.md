# Architecture

A short overview for contributors. It describes how ficsmap is put together and where things live. For setup and the branch workflow, see the [README](../README.md) and [CONTRIBUTING.md](../CONTRIBUTING.md).

## Overview

```
Browser (React SPA + Leaflet)            Server (Node 24, Fastify)            Storage
 ├─ features (map, panel, routes, ...) ─HTTP─► http ─► domain (rules) ──► SQLite (app.db)
 ├─ save.worker (save parser)                  auth (Discord OAuth2) ◄──► discord.com
 └─ SSE client ◄───────────SSE──────────────── sse hub (per world)
                                               static: SPA, dataset, tiles
```

One npm package, one process, one container. The server serves the API, the built SPA and the dataset files.

## Repository layout

```
src/shared/     types and pure logic used by server and web
src/server/     Fastify server
src/web/        React SPA (Vite root)
scripts/        build-dataset.ts (dataset build, including resource-nodes.json), cave-geometry.ts (cave sampling for it), heightmap.ts (height map tiles for it), map-areas.ts (biomes from the game's map areas), game-docs.ts, transport.ts, recipes.ts and machines.ts (vehicle, item, recipe and machine data from the game's Docs files), icons.ts (the dataset part `icons`: pictures of items, machines, vehicles and buildables from the extractor's `--icons-out`), buildings.ts (the dataset part `buildings`: footprints, names and categories of every buildable from the extractor's `--buildings-out` and the Docs), trace.ts (outline tracing), inspect-save.ts (dump a save for checks)
data-src/       extraction tooling and notes (extractor/README.md, the AssetsExtractor patch, item names)
test/           unit/, api/, web/, fixtures/
data/           local datasets, data/<game-version>/ (git-ignored)
```

### src/shared

- `collectibleTypes.ts`: the type registry (blue/yellow/purple slug, Somersloop, Mercer Sphere, hard drive). Each entry has its id, label key, marker style and the class matcher used by the dataset build. Sidebar, filters, markers, list view, counts and routes all iterate over it.
- `dataset.ts`: the dataset format and `indexDataset()` (lookup by actor name, aliases).
- `extract.ts`: turns a parsed save into the list of collected actor names.
- `route.ts`: route length and the optimiser (nearest neighbour, then 2-opt and Or-opt). `MAX_ROUTE_STOPS = 30`.
- `geo.ts`: world to map coordinates (100 world units = 1 m), point-in-polygon.
- `biomes.ts`: loads the hand-drawn biome polygons (last fallback) and assigns items to them. The primary source is the biome raster classified from the wiki's biome map (`scripts/wiki-biomes.ts`, read by the build with `--biome-raster`), then the game's map areas (`scripts/map-areas.ts`); both give biomes, outlines (traced with `scripts/trace.ts`) and item assignment from the raster.
- `caves.ts`: the extractor's cave volumes and the `caves.geojson` format (the sampling itself is in `scripts/cave-geometry.ts`).
- `resourceNodes.ts`: the `resource-nodes.json` format, the purity mapping (the game spells `RP_Inpure`), the layer's filter (resource, purity, occupied/free) and counts, reading node overrides, randomisation settings and the extractors on nodes (building, clock speed, Power Shards) from a parsed save, applying a world's overrides to the default nodes, and the extractor summary.
- `nodeRates.ts`: extraction rates on resource nodes, pure: the extractors of `recipes.json` that fit a node (miners on solid nodes, the oil extractor on oil nodes, the resource well extractor on a well's satellites; none for cores and geysers), their rate at the node's purity (`PURITY_FACTOR` from `planner.ts`) and 100 %, and the rate of an extractor from the save import at its clock speed (a well extractor at its pressurizer's).
- `heightmap.ts`: the height map tile format (`height/meta.json`, delta-coded int16 tiles in gzip) and the cell lookup.
- `transport.ts`: the vehicle calculator: the `transport.json` format and the pure maths (one-way trip, round trip, vehicles for a target rate, rate for a number of vehicles, fuel per round trip and per minute, `tripsByFuel`: one vehicle with each of its fuels at the game's speed for it, for the drone).
- `vehicleRoute.ts`: the vehicle calculator's route on the map: start and destination in world units, the straight-line length, and with both heights the height difference and the 3D length.
- `recipes.ts`: the `recipes.json` format (items, production recipes with alternates, production buildings, extractors, the resource well pressurizer, clock speed values) and `indexRecipes()` (producers per item with the default first, consumers, extractors per resource, `recipeTerms()` for a search). Reusable beyond the planner.
- `machines.ts`: the `machines.json` format of the machine and vehicle wiki, its stats rows, search, the entry's descriptor class (its picture), and the tier filter (`tierOptions`, `matchesTiers`, `toggleTier`, `upToTier`: groups `T0`…`T9` from the entry's unlocks, the HUB upgrades counting as tier 0, plus MAM, AWESOME Shop and other).
- `icons.ts`: the picture index of a dataset (`icons/items/index.json`: sizes and descriptor classes), file paths and the size to load for a display size.
- `buildings.ts`: the `buildings.json` format of the factory map (every buildable and vehicle class a save can hold: names, category, footprint boxes in the actor's frame, grid size of structural pieces, picture, the owner of parts), `indexBuildings` (case-insensitive lookup by class, classes per category) and `footprintRect` (2D outline without soft boxes).
- `planner.ts`: the production planner's core, pure: targets and choices in, steps (building, recipe, counts, rates, power) and totals out. One balance per item, solved as a linear system, so loops in the recipe graph need no recursion; loops that cannot work are reported. By-products enter the balance of their item; a step they oversupply gets no buildings and its balance becomes "at least the demand" (repeated until none is left; two steps running the same recipe are not coupled). Clock speed per step (`clockLimits`: minimum and +50 % per Power Shard from the data, up to 3 shards, so 1 %–250 %) and node purity per step; a resource well step runs at its pressurizer's clock speed (the shards and the pressurizer's power, per well, are reported apart from the totals' power); a picked recipe whose ingredient's default recipe would need the picked item back makes that ingredient "supplied from outside" (`auto: 'loop'`). Default per item: extract a resource (solids with the miner setting), else the first of `rankProducers` (main product before by-product, standard before alternate, unpacking last), else "supplied from outside". `choiceOptions` offers every extractor on its own (each miner tier, pumps, wells), so one step can run on another miner than the setting; `offeredChoice` names the setting's miner for a step that follows it. `totals.shards` counts the Power Shards of all buildings (per step its shards × its rounded-up buildings; not the pressurizers of resource wells, whose number depends on their sub-nodes); `evenClock` is the clock speed at which the rounded-up count makes the same (rounded up to 0.01 %).
- `factory/snapshot.ts`: the factory snapshot format (one save's factory for the factory map and its timeline) and the timeline's `SnapshotSummary`; `factory/analysis.ts`: the factory's efficiency, pure (see "Factory efficiency"); `factory/storage.ts`: the upload limits and `snapshotFigures()` (the summary's counts); `factory/retention.ts`: which old snapshots are thinned (see "Factory snapshots"); `factory/connections.ts`: the belt and pipe links and power circuits read from a save; `factory/lines.ts`: production lines built from the links (see "Production lines"). See "Factory snapshots".
- `api.ts`, `sse.ts`: DTOs and the SSE event union, shared by server and client.
- `saveUpload.ts`: the save watcher's upload limits and the upload token format (see "Save watcher").
- `i18n.ts`: locale detection, used by the SPA and the server-rendered invite page.

### src/server

```
main.ts         start-up: config, database, dataset, app, housekeeping
app.ts          Fastify instance, global hooks (CSRF, headers, rate limit, errors), route registration
config.ts       environment parsing (zod)
db/             db.ts (open, WAL, foreign keys), migrations.ts
auth/           discord.ts (OAuth client), session.ts, guards.ts (requireMember, requireAdmin, requireOwner)
domain/         business rules without HTTP: users, worlds, marks, importSave, invites, routes, resourceNodes, snapshots, uploadTokens, saveUpload
parse/          server-side save parsing for the save watcher: worker.ts (worker_threads), pool.ts (queue, timeout), header.ts
http/           thin route handlers, one file per area
sse/hub.ts      in-memory fan-out of world events
version/        app version, version guard, maintenance-mode app, rollback command
housekeeping.ts hourly purge of sessions and used invites, thinning of factory snapshots, daily backup
```

Rules live in `domain/`. Handlers in `http/` parse the request with zod, call the domain and broadcast SSE events. A feature with its own data adds a migration, a domain file and an http file.

### src/web

```
main.tsx, App.tsx, router.tsx
app/            api client, query keys, zustand store, user preferences (prefs.ts), i18n (en.json, de.json), theme.css, feature.ts
components/     shared primitives (see "Design system"): Button, Window, Dialog, SectionHeading, StatRow, Badge, NumberField, Fold, icons, ...
features/       one folder per feature
save.worker.ts  save parsing in a Web Worker
```

Features are modules that plug into extension points. `src/web/app/feature.ts` defines `FeatureModule`:

- `routes`: extra pages of the app (outside a world)
- `pages`: pages of their own inside a world, under `/w/:id/<id>`, at the full width of the main area (see below)
- `sidebarPanels`: panels in the sidebar (and the mobile bottom sheet)
- `mapLayers`, `mapControls`: components inside the Leaflet map
- `mapOverlays`: free-standing boxes over the map that position themselves (e.g. the route's "Bring with you" list)
- `mapModes`: exclusive click modes (inspect, route editing, picking the vehicle calculator's route); a mode with `onMapClick` takes points anywhere on the map
- `itemDetailSections`, `itemActions`: content and buttons in the item panel
- `headerItems`: things in the top bar; `slot: 'center'` puts one in the middle (the search), the default `start` after the world name
- `tools`: switches and actions in the top bar's tool navigation (see below)
- `searchProviders`: sources of results for the header search (see below)
- `settingsSections`
- `sseHandlers`: reactions to server events

All features are listed once in `src/web/features/index.ts`. `collect()` flattens one extension point over all features and sorts by `order`. The current features are `worlds`, `marks`, `live`, `map`, `progress`, `biomes`, `caves`, `coords`, `resourceNodes`, `itemPanel`, `routes`, `import`, `conflicts`, `sharing`, `listView`, `search`, `vehicleCalc`, `machineWiki`, `factory` (factory snapshots, the shared factory view and the world page `factory`; see "Factory snapshots" and "Factory efficiency"), `factoryMap` (the factory drawn on the map with its timeline; see "Factory map"), `saveWatcher` (upload tokens and the script generator in the world settings; see "Save watcher") and `planner` (production planner: the world page `planner`; its plan is remembered per device in `usePlanner`). The vehicle calculator (`vehicleCalc`, the world page `vehicles`) keeps its form and picked route in `useVehicleCalc`, per world and remembered on the device (`loadVehicleCalc`/`saveVehicleCalc` in `persist.ts`, key `ficsmap:vehicles:<world>`; the page and the route layer call `useVehicleCalcWorld(worldId)`, which loads a world's state when it is entered, and every change of the form or the route is saved); anything else can open it by navigating to `vehiclesPath(worldId)`, with a route length after `setForm({ route })`. Its "Pick on the map" turns on the map mode `vehicle-route` (`PICK_MODE`), sets the main view to the map and navigates to the map with the history state `PICK_STATE`. The mode's `onMapClick` and `onMarkerClick` feed `pick()`: start, then destination, which sets the route and the route length (the straight line in whole metres), leaves the mode and sets `returnRequest`; Esc or Cancel in the mode's banner (`cancelPicking()`, the `Button` primitive, 44 px on a phone) leave it the same way without a new route. While a mode with `onMapClick` is on, the collectible markers fade like the non-matches of a search (`MapView` passes `search: false` to `markerVisual`), so the picked points stand out. `PickReturn`, a map layer of the feature, carries the request out: a step back in the history when the map's entry is the one the picker pushed (so after the round trip Back leads where it led before), else a navigation to the calculator. Another map mode taking over ends picking without going back; opening the calculator page (the tool, Back) ends a pick still going on (`stopPicking()`). The route stays on the map as a layer (A, B and the line, draggable); the line has its own pane (`ROUTE_PANE`, z-index 460) above the marker canvas (450) and the resource nodes (455) and below Leaflet's marker pane with the pins, without pointer events. The page shows the game's pictures of the vehicles and fuels through `IconsContext`. It is built from the design system: three numbered step windows (route, vehicle, fuel; the number in the accent before the title) and "More settings" (a `Fold` with the values in effect), beside them the result window; the page uses the full width (from 1280 px the steps keep 36rem and the result takes the rest). The route step shows a picked route in one line (A–B and the height difference from the height map; not the straight line, which the length field right under it holds or, once typed, offers back; no 3D length, the model does not use it) with [Pick again] and [×], then the length field with one hint (roads or rails are longer, drones fly the straight line) and, once the length is typed, a button that takes the straight line again. With a picked route the drone always flies its straight line (`vehicleSetup` in `format.ts` takes it as the drone's route length, `fliesStraight`); a typed length is for the ground vehicles, and while it differs the drone's card, the field's hint ("For ground vehicles; drones fly the straight line (1,503 m)") and the drone's result ("Straight line 1,503 m · 180 km/h") name the straight line. Once a length above 0 is known, every vehicle card shows what that vehicle moves per minute with its own inputs in effect (`cardRates` in `format.ts`: its typed or game speed and stop time, the drone's own fuel and straight line), whole numbers from 100 up and one decimal below (`cardValue`), so the cards are the comparison. The result window names the assumption in its title bar ("Straight line · 90 km/h"), on narrow pages (below `lg`, where the inputs are not beside it) also vehicle, length and fuel, then the big figures as `StatTile`s (stacks or m³ per minute, round trip and one way in whole seconds, fuel per trip and per minute) and, folded inside it, the fuel comparison and the fleet question (its answer the vehicles needed as the main `StatTile` beside the utilisation, under them what they move together and their fuel as a `StatList`). The note on the fuel estimate names the extra use uphill only for the Tractor and the Explorer. The fuel comparison is closed at first: for wheeled vehicles its summary repeats the chosen fuel per minute ("Packaged Fuel · 8.7/min"; one column, fuel per minute: the trip takes as long with every fuel), for the drone it names the fastest (round trip, fuel per trip, stacks per minute); the selected fuel is pinned on top (`pinSelected`). Fuel amounts show one decimal from 1 up, two significant digits below, "< 0.01" below that (`formatFuel`). The visible result is no live region: one sentence per answer ("Truck: 18 stacks/min, round trip 2 min 40 s, 24 Packaged Fuel per trip", and the fleet's answer) goes to a visually hidden status region once the input has not changed for 500 ms; visually hidden elements sit in a `relative` box (cards, fields), so they cannot stretch the scrolling page. "Pick on the map" stays in the route step: it is the main way to enter the route, not a page action. The length follows the points (`lengthFromRoute`) until it is typed; a new pick always sets it. The length is the straight line: exact for drones, a lower bound for wheeled vehicles; real paths along roads, belts or rails are for a later route planner. The machine wiki (`machineWiki`, the world page `wiki` with the sub-path `:entry?`) keeps its search text and tier filter (remembered per device) in `useMachineWiki`; the open entry is the URL (`wikiPath(worldId, entry?)`), so choosing an entry is a navigation and Back goes through the entries. The search and the tier filter share one row where the width allows: toggle chips (several tiers at once, so tiers 0 to 4 is "up to tier 4"), one "Up to tier" select that sets tiers 0 to n in one go, [× Clear filter] only while a tier is chosen, and "n of m shown" only while something is filtered. An open entry is a `Window` (`as="article"`) laid out like the planner's machine window: the title bar with the entry's picture, its name, the name in the other language and its category, and its tier `Badge`s; then `SectionHeading` sections: the stats as a `StatList`, the fuels as a `StatList` with pictures, the game's description, build cost, unlocks, the recipes in a `Fold`, and the wiki link in the footer. The clock speed row gives the range with Power Shards: the entry's own range plus `MAX_SHARDS` (from `planner.ts`, as in the planner) times what one shard adds (`clock.perShard` of `recipes.json`, loaded once an entry that has a clock speed is open); without the recipe data it says the range without shards. On a phone (below 640 px) the list or the entry shows, and the entry has no × of its own: the back control above the page leads to the list (`usePageBack`). Its pictures come through `IconsContext` and `GameIcon` (`features/machineWiki/icons.tsx`, exported for other features; the resource node panel and info box use them too), which renders nothing, or an empty box of the same size, when the dataset has no picture or the file fails to load.

**World pages** (`WorldPage` in `app/feature.ts`, helpers in `app/pages.ts`). A feature's `pages` entry (`id`, optional `subPath`, `titleKey`, `Component`) is a page under `/w/:id/<id>`; the id is the path segment, short lower-case English. Today: `factory` (the factory's efficiency and timeline), `planner` (production planner), `vehicles` (vehicle calculator) and `wiki` with `subPath: ':entry?'` (machine wiki, `/w/:id/wiki/<entry id>`, e.g. `Build_ConstructorMk1_C`). `appRoutes()` (`router.tsx`) adds every page as a child route of the world route (route id `WORLD_ROUTE_ID`, `/w/:id` from the `worlds` feature, next to `settings`), so `WorldLayout` with the event stream, the stores and the header stays mounted. The world layout asks `useWorldPage()` (the page matching the URL) and then shows `WorldPageView` in place of the sidebar, the map, the item panel and, on mobile, the sheets: the page at full width, scrolling on its own (a `relative` box, so absolutely placed screen-reader texts stay inside it), rendered through the route's `<Outlet context={ctx}>` (the page gets the world as `ctx` and reads its sub-path with `useParams()`). There is no page header: the tab (from 1280 px) or the section menu (below) already names the page, so the page heading (an `h2`, the name of the page's `main` landmark, the same word as the tab) is `sr-only`, and a page keeps its actions in its own windows' title bars. The way back to the map is the Map tab or menu entry. Only a page that points a back control somewhere inside itself with `usePageBack({ to, label })` (`components/PageActions.tsx`; the wiki from an entry to its list on a phone) gets a bar above it with that control ([← label]). The view is keyed by the page, so the keyboard focus moves to the heading when a page opens, not when a page changes its own sub-path. The browser tab names the section and the world ("Planner · Letz Fetz · ficsmap"; `useWorldTitle` in `WorldLayout`, the map is "Map", the settings "Settings"), and says "ficsmap" again once the world is left. On a page the top bar keeps the search and the section navigation, but not what only acts on the map: header items with `mapOnly` (Import, the biome scope) and the map's switches (the settings page has neither search nor navigation). `worldPath(worldId, ...segments)` builds the paths. A page keeps its state in a store, so it is still there after a visit to the map.

**Map requests.** Code that is not on the map asks it to do something through a request in a store, which the map carries out when it is shown and then clears: `focusItem` (`focusRequest`, select and zoom, carried out by `SelectionPan`), `setBiomeScope` (`biomeFitRequest`, fit to the biome, by `BiomeLayer`; a scope restored with the view makes none) and `useMapFit` (fit to an area, by `MapFitLayer`). So a search result chosen on a world page or in the list view acts on the map once it is back.

**Planner page.** `Planner.tsx` lays the page out as input beside answer, like the vehicle calculator: the window "What do you need?" (the wanted items, each an `ItemPicker` with the item's picture and a `NumberField` for the rate; the extractor defaults folded away in a `Fold` whose summary shows the values in effect; the purity factors are in its hint) and beside it, below it on a phone, the compact window "Totals": power as the main `StatTile` (and the Power Shards of all buildings when a step needs some) in one row with the raw resources with their extractors ("40× Miner Mk.1"), items supplied from outside and the surplus, each a grid of `StatRow`s with the game's pictures in as many columns of at least 14rem as fit (so a long plan grows sideways first), and the buildings by kind in a `Fold` closed by default whose summary is their total. No exact counts there (they are in the node's tooltip and the step panel). A raw resource mined on nodes (an extractor with `onNode`) whose resource the dataset's `resource-nodes.json` has gets "Show on map": a link to the map that first calls the node layer's `showResource` with that resource and the step's purity (the settings' one unless the step has its own) and sets the main view to the map; the node file is fetched only for such a plan. Under both the window "Production steps" with the diagram or the list; its title bar holds the view switch (Diagram | List; below 400 px only the icons show, the words stay the radios' names) and, for a diagram wider than its box, "Fit to width" (not on a phone below 640 px, where the text would be a few pixels high). "Start over" (once something is entered) sits in the title bar of "What do you need?"; it shows a toast with `focusAction`, so its Undo takes the keyboard focus, and Undo restores the plan (`reset` returns it, `restore` puts it back) and moves the focus to the first item picker. The view is remembered once the user picks one (`viewChoice` in the stored state); until then a phone (below 900 px) shows the list and a wider screen the diagram (`usePlannerView`). Before anything is picked the totals window says in one sentence what will appear, with the game mode note, and offers an example (`EXAMPLE`, Reinforced Iron Plate at 5/min, only when the dataset has the item). A plan error is shown above the totals; the last working plan stays below it. Screen readers hear the totals as one sentence ("2,550 MW, 365 buildings") in an `sr-only` status, half a second after they last changed.

**Planner diagram.** The planner shows its steps as a material flow from top to bottom (`features/planner/PlanDiagram.tsx`) or as a table (`StepList.tsx`). The drawing is generic and shared with the factory's production lines: `layoutGraph(nodes, links)` in `diagramLayout.ts` lays out any graph whose nodes have a row (and optionally a width of their own) and whose links join two nodes (down, up or within a row); with `direction: 'right'` the rows become columns (the layout runs in the flow's own axes and only the result is turned: edges leave a node's right side and enter the next one's left, a by-product pointing back enters the right side, a loop arcs left of its column, a column is as wide as its widest node while each node keeps its measured height, labels sit on a straight piece left of the arrowhead and stagger sideways), and `FlowDiagram.tsx` draws it (the canvas, measuring, panning and zooming, keyboard, hot and faded edges) with the caller's node content, edge looks and labels; `PinnedPicture` (`pictures.tsx`) is the building picture with its product pinned to the corner. `layoutDiagram(steps)` lays the plan out, pure and deterministic: a step's row counts from the extraction side (`maxDepth - depth`), steps without inputs (extracted, supplied from outside) move to the top row, and a wanted item nothing else uses stays in the bottom row with the other wanted items. Every item is one node; an edge runs from the step making an item down to each step using it (with the rate), a by-product edge from a step to the step its by-product covers (pointing up into its bottom when that step sits higher), and loop edges stay inside their row as arcs above it. An edge spanning several rows gets a lane in each row it passes, so it runs between the nodes there. Nodes and lanes are ordered per row by barycenter sweeps (keeping the order with the fewest crossings) and placed as close to their neighbours as that order allows (isotonic regression). A row is as high as its tallest node: the page measures each node's content after rendering (`heights`, before the browser paints; again once the web fonts are in) and lays out again when that differs. Edge ends are spread over a node's top or bottom side in the order of where they come from; the rate label (the item's 16 px picture and the rate) sits on a straight piece above the arrowhead, labels at one side are staggered in height where their ends are closer than a label is wide, and the gap between two rows grows with them. The edges of the selected and the hovered or focused node are drawn thicker on top; with a step selected the others fade to half. The diagram sits on a dotted canvas in its window; the keyboard help is its `sr-only` description, and a legend below only appears for by-products, loops, items supplied from outside or Power Shards. The diagram moves like a map (`FlowDiagram`, the math pure in `viewport.ts`, `test/unit/diagramViewport.test.ts`): the content is one layer with a CSS transform (translate and scale; the SVG edges and the HTML nodes stay aligned, `will-change` only while it moves so the text is drawn sharp again afterwards) in a clipped box (`overflow: clip`, so `scrollIntoView` never scrolls it) as high as the diagram, at most 70 % of the screen, on a dotted canvas that moves and scales with it. The view lives in a small store outside React state, so a drag renders nothing again; only the zoom keys and fades subscribe. A press and drag pans (on a node only past 4 px, 8 px for a finger, and the click that ends a drag is swallowed, so a plain click still opens the node), two fingers pinch around their midpoint, a double click on the canvas zooms in (with Shift out). The mouse wheel zooms around the pointer at the user's wheel speed (profile setting, `getWheelSpeed`; deltas in pixels as the map counts them, `wheelDeltaPx`, a notch at 1× about 1.2×), but only once the diagram is engaged: the mouse moved over it (a `pointermove` with movement), pressed in it, or the focus is in it; a page scrolled past a still pointer keeps scrolling. A trackpad pinch (a wheel with Ctrl) always zooms, a sideways swipe pans. A finger drag pans; where the diagram fits the box's height, `touch-action: pan-y` leaves vertical swipes to the page. Zoom limits 25 % to 200 % (out further only as far as fitting the whole diagram needs). The keys in the top right corner (−, the zoom in % that resets to 100 %, +, "Fit": the whole diagram, refitted on a resize) are 32 px, 44 px below 900 px, like the map's. The view opens at 100 % with whole nodes of the top row (`initialView` with `initialScroll`: the longest run of neighbouring top-row nodes that fits, nearest the middle, centred; a little lower so the zoom keys do not cover a node), re-opens while the layout settles and starts over when the nodes or the direction change (the same nodes with new numbers keep the view); a fade on each side it continues. The diagram runs top to bottom or left to right (`layoutGraph`'s `direction`, see below; the title bar's `DirectionSwitch`, remembered per device and diagram in `ficsmap:diagramDirection:planner` / `:lines`; below 480 px always top to bottom, without the switch). Each step shows how fully its buildings are used (`stepUtilisation` in `src/shared/planner.ts`: the exact count over the built one, 1 for a whole count; `utilisationBand`: full only at 100 %, nearly full from 90 %, else part load, in the factory's band colours): a strip on the node's left edge (solid green, dashed yellow, dotted orange, `USE_STRIP`) and the value ("100 %", "99.1 %", never 100 % unless it is) after the rate, in the accessible name ("Buildings used to 99.1 %"), in the table's buildings column and in the panel; the legend lists the bands once a step is not fully used; steps without buildings stay neutral. A node is a compact button side by side: the step's building picture (`pictures.tsx`: `Build_X_C` -> `Desc_X_C` from the dataset part `icons`, through the machine wiki's `IconsContext`) with the product's picture pinned to its corner (`StepPicture`; an item supplied from outside or covered by by-products shows the item's own picture, the former in a dashed frame; without a picture an empty tile of the same size), then "4× Constructor" (rounded up, the exact count as tooltip), the item (wrapping, never cut), its rate with compact badges (`StepBadges`: wanted, loop, alternate recipe, a purity other than the settings' one, clock speed with one diamond per Power Shard, by-products), and a third line only for by-products or why it is supplied from outside. `stepText.ts` makes these texts and the node's accessible name for both views. One tab stop; the arrow keys move within a row (left/right) and to the nearest node of the row above or below (left to right the other way round); a node that gets the focus from the keyboard or a closing panel is panned into view; Shift and the arrows pan, + and − zoom around the focused node, 0 shows 100 %; Escape closes the open panel. It sits beside the steps from 1280 px (sticky; selecting a step does not scroll the page there, so the totals stay in view) and below them on narrower screens, scrolled into view when a step is selected (smoothly only where motion is welcome).

**Top bar.** `components/Header.tsx` has three parts: the ficsmap mark (a link to the world list), then the sidebar toggle, the world name and the `start` header items (live state, Import, Settings) on the left; the `center` items (the search) in the middle; below 1280 px the section menu and, after a divider, the account menu on the right. With a middle both sides grow from zero alike, so the search stays centred; the right side never shrinks below its content and the left side gives way (the world name truncates), so nothing overlaps. Below 1280 px the mark and Import show without their words (which stay for screen readers and tooltips), so the world name keeps its room; the live state then shows its word only when something is wrong (connecting, offline), and its mark has a shape per state (dot, ring, cross), so colour is never the only cue. On mobile (below 900 px) there is no middle: the search is a button next to the section menu and opens over the bar, the mark gives way to the world name (the account menu leads to the worlds), and the right side takes just its content. From 1280 px the tab strip of the sections follows the bar (see Navigation). The settings page shows neither search nor navigation; the world pages show both.

**Navigation and tools** (`Tool` in `app/feature.ts`). A tool describes itself (`id`, `order`, `labelKey`, optional `hintKey`, `icon`, `shortcut`) and has a hook `useTool(ctx)` that returns `{ available, pressed?, run }`: `available: false` hides it (e.g. no caves in the dataset), `pressed` makes it a switch (aria-pressed, a filled button), without it the tool is a plain action (`action: true`). A tool with `page` is a section of the world: `pageTool({ id, order, labelKey, hintKey, page })` from `app/tools.ts` builds one; its label is the section's one word, and the page's heading should be the same word. `features/worlds/ToolsNav.tsx` renders them, so a tool never renders itself. From 1280 px `WorldTabs` is a tab strip under the top bar: [Map | Factory | Planner | Vehicles | Machines], an icon and a word each, links with `aria-current="page"` on the section shown, which has an accent underline as in the game's tabbed menus; on the map the map's switches and actions follow at its right end as one bar of buttons (`role="group"`, "Map layers"). Below 1280 px and on phones `SectionMenu` is one menu button in the top bar named after the section shown ("Map ⌄" with its icon; a WAI-ARIA menu button), listing the sections ("Sections", link items, Enter or Space) and, on the map, the map's switches ("Map layers", `menuitemcheckbox` entries). The map's switches are never shown on a world page, where they would do nothing. Today: Collectibles (10), Caves (20), Height map (25), Resource nodes (30); pages Factory (35), Planner (40), Vehicles (50), Machines (60).

A map switch kept in a `{ visible, toggle }` zustand store moves from `mapControls` into the tool navigation by replacing its control entry with one line, using `toggleTool()` from `app/tools.ts`:

```ts
// before: mapControls: [{ id: 'resource-nodes', order: 22, Component: ResourceNodeControl }],
tools: [toggleTool({ id: 'resource-nodes', order: 30, labelKey: 'resourceNodes.control', hintKey: 'resourceNodes.hint', useToggle: useNodeLayer, useAvailable: ctx => Boolean(useResourceNodeFile(ctx.me.datasetVersion)) })],
```

The control component can then be deleted. `useAvailable` is a hook too (it may load something, like the heights' `meta.json`); leave it out when the switch always applies.

**Search** (`features/search`). The search box knows nothing about what it finds. Every feature can add a `SearchProvider` whose hook `useEntries(ctx, active)` returns `SearchEntry` objects, or undefined while its data loads. `active` turns true once the user opens the search, so providers with large files (caves) load them only then. An entry has an `id`, a `label` (current language), an optional `detail` line and `icon`, a `kindKey` ("Biome", "Cave", ...), `terms` (IDs, the name in the other language, synonyms), the `actors` it stands for and an `onSelect(ctx)`. Providers today: collectibles (types and single items, in `search`), biomes, caves, resource nodes (one entry per resource and one per resource and purity; choosing one switches the node layer on with only that resource), crash sites and the machine wiki's machines and vehicles (in their own features). Recipes can be added later as one more provider in a recipes feature; entries without `actors` simply leave the map as it is.

Matching and ranking (`features/search/match.ts`) are pure functions: text is normalised (case, accents, ß), and an entry matches when a term contains the whole query or when every word of the query starts a word in some term. Exact term before prefix before word start before inside a word, a match ending at a word end before one that does not ("Dune Desert 3" before "... 30"); ties go by the entry's `weight` (default: the provider's `order`; types 0, biomes 10, caves 20, items 30, resource nodes 35, crash sites 40), then by label in natural order. Queries under two characters match nothing.

Results show their label and a `detail` line where it helps (a type's count, a cave's biome, what a pod needs); a single collectible's actor ID is a search term but not shown. Crash sites are found by what lies there and their threats, not by their notes (prose such as "a Somersloop is on the same island" would make the site a Somersloop match and add its pod to the highlight). While a query is typed, the union of the matches' `actors` goes into the store's `searchHighlight`; after a choice, the chosen entry's `actors`. On mobile, closing the search over the bar without a choice clears it (nothing stays dimmed out of sight); a chosen result about the map (one with `actors`, also an empty list such as a resource) shows as a chip under the bar ("Search: Somersloop ×"): the chip reopens the search, its × ends it. The map's marker canvas reads it like the other filters: matches get a halo in the accent colour and are drawn on top, even where a filter would hide them; everything else fades to 20 %. Choosing an item calls `focusItem` (select and zoom, like "Show on map"), a biome sets the biome scope, a cave switches the cave layer on and asks `useMapFit` (a map layer of the search feature) to fit the view to it. An entry with `actors` is about the map: chosen on a world page, the search box first navigates to the map, then calls `onSelect`, whose requests the map carries out once it is shown (see "Map requests"). A machine of the wiki navigates to its wiki entry. `features/mobile` is not a feature module; it holds the bottom sheet the world layout uses on small screens. A new feature should add a module here rather than edit core screens.

## Backend

**Stack.** Fastify 5, better-sqlite3, zod, jose, @fastify/cookie, @fastify/static, @fastify/rate-limit.

**Database.** One SQLite file (`DB_PATH`, `/data/app.db` in the container), WAL mode, foreign keys on. Tables: `users`, `identities`, `sessions`, `worlds`, `world_members`, `invite_uses`, `marks`, `routes`, `resource_node_overrides`, `resource_node_extractors`, `factory_snapshots`, `upload_tokens`. `users.prefs` (migration 7) holds the user's preferences as a JSON object (see "User preferences"). Migrations are an append-only list in `src/server/db/migrations.ts`; entry *i* sets `PRAGMA user_version` to *i*+1. Never edit a released migration; append a new one.

**Marks.** A row in `marks` means "collected" for one actor in one world, with `mismatch` (conflict flag), `updated_by` and `updated_at`. Each world has a `rev` counter that is bumped on every change and sent with SSE events.

**Resource nodes.** The default nodes are static dataset data (`resource-nodes.json`). A world's own resource and purity per node, as its last save import reports them, are world data on the server: rows in `resource_node_overrides` (node, resource, purity) and the save's node randomisation settings in `worlds.node_settings` (JSON). The extractors standing on nodes in that save are rows in `resource_node_extractors` (node, `seq` per node, kind `miner1`/`miner2`/`miner3`/`oil`/`pressurizer`/`well`/`geothermal`/`portable`, clock speed with 1 = 100 %, Power Shards; clock and shards null for extractors that cannot be overclocked, the portable miner and the geothermal generator). They live on the server, not in the importing browser, because only the owner and admins import while every member should see the world as it is; they are replaced by every import that sends node data (older clients send none and leave them alone; extractors likewise only when the request has `extractors`). Members read them with `GET /api/worlds/:id/resource-nodes` (`{overrides, settings, extractors}`, `src/shared/api.ts`); the client merges them over the default nodes and refetches on the `import` event.

**Authentication.** Discord OAuth2 authorization code flow with PKCE (S256) and a `state` check. The transaction (state, verifier, return path, optional invite token) is kept in a signed, HttpOnly cookie for ten minutes. After the callback the Discord token is used to read the profile and then discarded. A new account is only created for an ID in `OWNER_DISCORD_IDS` or together with accepting a valid invite, in one transaction.

**Sessions.** A random 32-byte token in the HttpOnly cookie `sid` (SameSite=Lax, 30 days). Only its SHA-256 hash is stored.

**User preferences.** Settings of the user rather than of a world live on the account, so they follow the user to every device: `users.prefs`, a JSON object whose keys and checks are in `src/shared/prefs.ts` (`UserPrefs`; a missing key has its default). Today there is one key, `wheelSpeed` (0.25–3 in steps of 0.05, default 1). `GET /api/me` returns them as `prefs`; `PATCH /api/me/prefs` takes a partial object (zod, unknown keys and bad values are 400 `invalid_body`), merges it into what is stored and returns the whole result. Invalid stored values are dropped when read. The language is not one of them: it stays a setting of the device (`localStorage`), because the sign-in page needs it before anyone is signed in.

**Invites.** HS256 JWTs signed with `INVITE_JWT_SECRET` (issuer `PUBLIC_URL`, audience `ficsmap:invite`, subject = world id, random `jti`, 7-day expiry, `ep` = the world's invite epoch). The compact JWT is Base64url-encoded once more for the link `/invite/<token>`; only the canonical encoding is accepted. Opening a link never consumes it. The token is consumed in the transaction that adds the member, by inserting its `jti` into `invite_uses`, so it works once. Revoking bumps the world's epoch, which invalidates all open links.

**CSRF.** Every POST, PUT, PATCH and DELETE must carry an `Origin` equal to the origin of `PUBLIC_URL` and a JSON content type (an empty DELETE is allowed). This runs in an `onRequest` hook for every request, so it also covers unknown paths. Together with SameSite=Lax cookies this blocks cross-site writes. The one exception is the save watcher's upload (`POST /api/worlds/:id/saves`, matched on the route pattern in `BEARER_ROUTES`): it takes a bearer token and never reads the cookie, and a cross-site page cannot set `Authorization`.

**Security headers.** `X-Content-Type-Options`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY` and `frame-ancestors 'none'` on every response unless a route sets its own.

**Rate limits** (per IP unless noted):

- 300/min globally for `/api`, `/auth` and `/invite`; static GETs (tiles, assets, dataset, SPA shell) are exempt
- 10/min for `/auth/*` and `/invite/:token`
- 6/h per world and user for save imports
- 120/min for mark writes, 30/min for route writes
- 60/min per user for preference writes (`PATCH /api/me/prefs`)
- 120/h per world and user for factory snapshot uploads
- 60/h per upload token for the save watcher's uploads (`POST /api/worlds/:id/saves`), 30/h per user for creating upload tokens

**Permissions.** A world has one owner (`worlds.owner_id`), admins and members (`world_members.role`: `member` or `admin`, migration 6; the owner's own row keeps `member`). `roleOf` gives `owner`, `admin` or `member`; `src/shared/roles.ts` has the type and `hasRole`/`canAdmin` for both sides. `requireMember`, `requireAdmin` (owner or admin) and `requireOwner` run as preHandlers on every world route, the event stream included. Non-members get 404, members without the role 403 `forbidden`. The world DTO and the member list carry each role.

| Route | Owner | Admin | Member |
|---|---|---|---|
| `GET /api/worlds/:id`, marks, routes (read and create), resource nodes, snapshots (read), events | yes | yes | yes |
| `PUT`/`DELETE /api/worlds/:id/routes/:routeId` | yes | yes | own routes |
| `PATCH /api/worlds/:id` (rename) | yes | yes | no |
| `GET /invite-link`, `POST /invite-links/revoke` | yes | yes | no |
| `POST /import`, `POST /snapshots`, `DELETE /snapshots/:sid` | yes | yes | no |
| `GET`/`POST /upload-tokens`, `DELETE /upload-tokens/:tid` | yes | yes | no |
| `DELETE /members/:userId` | anyone but themselves | plain members, and themselves | themselves |
| `PUT /members/:userId/role` | members and admins | themselves to `member` | no |
| `DELETE /api/worlds/:id` | yes | no | no |

`PUT /api/worlds/:id/members/:userId/role` takes `{role: 'admin' | 'member'}` and answers 204; the owner's role never changes (403), a non-member target is 404. Role changes and removals broadcast `members`, so every client refetches the world and with it its own role. Losing admin rights, leaving or being removed revokes the upload tokens that user created. The save watcher's upload is the one route without a session: its upload token stands for the user who created it (imports run under their name). Imports and snapshots also record who made them.

**SSE.** `GET /api/worlds/:id/events` keeps a `text/event-stream` open with a heartbeat. The hub keeps a `Map<worldId, Set<client>>` in memory and broadcasts events (`mark`, `marks-bulk`, `import`, `world`, `members`, `removed`, `deleted`, `routes`, `snapshots`). There is no replay: on (re)connect the client refetches and ignores events whose `rev` is not newer than what it loaded.

**Housekeeping.** Hourly purge of expired sessions and old `invite_uses`. One `VACUUM INTO` backup per UTC day to `backups/app-YYYYMMDD.db` next to the database; 14 are kept.

## Frontend

**Stack.** React 19, TypeScript, Vite, Tailwind CSS v4, react-router, TanStack Query, zustand, Leaflet with react-leaflet, i18next with ICU messages.

- **Server state** goes through TanStack Query. SSE handlers update or invalidate the query cache.
- **UI state** (selection, filters, interaction mode, sidebar) lives in one zustand store (`src/web/app/store.ts`). Parts of the view are persisted locally (`persist.ts`).
- **Map.** Leaflet with `CRS.Simple`; world coordinates map linearly to the tile image. All collectible markers are drawn on one canvas layer (`features/map/MarkerLayer.ts`) instead of one DOM element per marker. Below a zoom threshold markers are dots; above it they use the game icons. The layer has its switch in the tool navigation like the other layers ("Collectibles", `order` 10, the `map` feature's tool; `markersVisible` in the UI store, remembered per device by `loadMarkersVisible`/`saveMarkersVisible`, key `ficsmap:collectibles`, on by default and not reset by `enterWorld`). Off, `MapView` calls `MarkerLayer.setVisible(false)`: the canvas stays empty and `pick()` finds nothing, so clicks and hover see no marker (a mode with `onMapClick` gets the plain position); the type filters, the collected visibility, the progress panel, the list view, the item panel and the search keep working and apply again once it is on. What is about a marker switches it on: `select(actor)` (the item panel's nearby items, the conflict review, [Next stop ›], a marker click), `focusItem` ("Show on map", the search's items and crash sites), `setMode('route')` (the editor adds stops by clicking markers), opening a saved route (its stops are marker badges) and a chosen search result with `actors` (a type, a biome, a cave; `SearchBox`, not while typing). A result with empty `actors` (a resource), the filters themselves and the vehicle calculator's picking (it takes points anywhere) leave it as it is. Resource nodes have a canvas of their own (`features/resourceNodes/NodeCanvasLayer.ts`, drawing in `drawNode.ts`) in a pane above the collectible markers (`NODE_PANE_Z` 455: the pane exists only while the layer is on, and then the nodes are what the user looks for; below the vehicle route's line at 460): each node is its resource's picture from the dataset part `icons` (loaded once per session by `nodeImages.ts`, the canvas redraws when one arrives) on a dark plate in a ring of its purity colour (`--color-purity-*`; no pips, the colour alone tells the purity); until a picture is loaded, or for geysers (no picture), a disk in the resource colour (`--color-res-*`) takes its place. Zoomed out nodes are dots in the purity colour sized by purity. While the layer is on it registers a test in `features/map/clickClaims.ts`: a click in the `inspect` mode on a node is the node's (its box pins), so `MapView` does not also select a collectible under it. The node box puts the extraction rates on a line of their own. The sidebar panel has the purity filter right under the layer switch, then the resources, each with a visible "only" button (Alt-click still works). The header search finds the resources (`resourceNodes/search.tsx`): one entry per resource ("Iron Ore", detail "46 pure · 42 normal · 39 impure") and one per resource and purity ("Iron Ore · Pure", found by "iron pure" or "eisen rein"), whose `actors` are empty: the entry is about the map (on a world page the search goes to the map first; on a phone the chosen entry stays as the search chip), but the nodes are no collectibles, so nothing fades and the status counts no highlighted objects (drop pods next to the nodes stay visible); choosing one switches the layer on and sets its filter to that resource (and purity) with `showResource`, which isolates its nodes.
- **Map modes.** The store holds the active interaction mode. The map sends marker clicks to the active mode's handler; turning one mode on turns the others off. A mode with `onMapClick` takes points anywhere: the map gets a crosshair, a click away from the markers goes to `onMapClick` with the world position, a click on a marker icon to `onMarkerClick` (dots count as points and do not zoom in), and on mobile the panels sheet drops to peek and the item sheet closes when it turns on.
- **User preferences** (`app/prefs.ts`). A small zustand store fed by `useMe` (every `GET /api/me` hands its `prefs` to `receivePrefs`) and remembered in `localStorage` (`ficsmap:prefs`), so the last known values apply before the account has loaded. `setPrefs`/`useSetPrefs` apply a change at once and save it with `PATCH /api/me/prefs` 600 ms after the last change (one request at a time); until the server has it, the change wins over a newer `GET /api/me`, and a failed save keeps it (status `failed`, [Retry] on the profile page). The profile page (`/profile`, `features/worlds/ProfilePage.tsx`, from the account menu) shows the settings: the mouse wheel speed as a slider with [Default] and the save state, and the language switch.

  **Mouse wheel speed.** `useWheelSpeed()` returns the factor (1 = normal, 2 = twice as far per wheel turn, 0.25 … 3) and re-renders on a change; `getWheelSpeed()` reads it outside React, e.g. in a wheel listener that is set up once. Whatever zooms on the wheel scales its step by it; the flow diagrams (`wheelFactor` in `features/planner/viewport.ts`) zoom by `exp(-deltaPx × 0.002 × wheelSpeed)` per event, the delta counted like the map's (`wheelDeltaPx`). The profile page's slider moves over fixed stops (`WHEEL_SPEED_STOPS` in `src/shared/prefs.ts`: 0.25, 0.4, 0.5, 0.75, 1, 1.25, 1.5, 2, 3) so 1× sits in the middle; the API takes any value on the 0.05 grid.

  **Map wheel zoom** (`features/map/wheelZoom.ts`, `WheelZoom` in `MapView.tsx`). The map has its own wheel zoom instead of Leaflet's `scrollWheelZoom` (off), because Leaflet maps one wheel event through a curve and rounds up to whole levels, so its speed hardly changed anything (a mouse notch was two levels whatever the setting). A non-passive `wheel` listener on the map container (it calls `preventDefault`, so neither the page scrolls nor the browser zooms on ctrl+wheel, which is how touchpads send a pinch) normalises the delta to pixels (a line is 100/3 px, so Firefox's 3-line notch is 100 px; a page is the map's height), multiplies it by the speed and adds it up. Every 100 px is one whole level (`zoomSnap` stays 1 for crisp tiles and marker sizes): at 1× one notch is one level, at 0.5× two notches, at 2× one notch two levels; at most three levels per event. The rest carries over, so 0.75× zooms three levels per four notches. The zoom goes around the pointer (`setZoomAround`), within the map's min and max zoom, animated unless reduced motion is preferred. A half step is forgotten after 1 s without wheel events (long enough for slow, deliberate notches at 0.5×), and a turn the other way starts over. After a zoom a 120 ms cooldown lets at most one more level fill up, zoomed when it ends, and a step asked for while the previous zoom still animates waits for its `zoomend` (Leaflet would drop it; only one step waits). So steady scrolling zooms at most about one step per animation: a 3-second touchpad fling of 2,400 px went through 7 levels instead of 24. Touch pinch and the +/− buttons are Leaflet's as before. `wheelZoomStep` is a pure function (state, event, speed, time) and has its own tests.
- **i18n.** All strings are in `src/web/app/i18n/en.json` and `de.json`, in ICU syntax (plurals, numbers). The language comes from `navigator.languages`: German if the first matching entry starts with `de`, otherwise English. Missing German keys fall back to English.
- **Design tokens.** Colours, spacing and fonts are defined once in `src/web/app/theme.css` (`@theme`). Components use token utilities, not raw colours. See "Design system" below.
- **Mobile.** Below 900 px the sidebar becomes a bottom sheet (`features/mobile`; peek 112 px with a 44 px handle, half and full 50 % and 92 % of the screen) and the item panel an item sheet over it (half the screen, marked `data-item-sheet`; its footer with the coordinates scrolls with the sections instead of being pinned, so it takes no room from them); both sit on the bottom of the screen. At peek the sheet shows the progress chips in one row that scrolls sideways; while chips are hidden on the right, the row's right edge fades out (a CSS mask). A newly selected marker is panned above the item sheet's measured top edge plus 32 px (`SelectionPan`). The world layout is `h-dvh` with `overflow-hidden`, so nothing makes the whole screen scroll. A world page takes the whole screen under the header, without the sheets. Touch targets are at least 44 px there: small buttons and segments grow to it, the zoom keys too; form controls use 16 px text so iOS does not zoom into them.

## Design system

The look follows the game's FICSIT interface without copying its textures, logos or fonts: neutral gunmetal panels on a near-black base, off-white text, one orange accent for what is active or primary, condensed capitals for titles, thin rules, cut corners and a few hazard stripes. From Factorio: dense, but grouped, and every group has a heading.

**Tokens** (`app/theme.css`, the only place colours are defined; `test/web/theme.test.ts` checks them):

| Token | Use |
|---|---|
| `bg`, `panel`, `raised` | Surfaces, darkest first: page and map base, form fields; panels, sidebar, windows; title bars, hover and selected rows |
| `line`, `edge` | Hairlines between areas (decoration); the 3:1 edge of form controls |
| `fg`, `muted` | Text and secondary text (both at least 4.5:1 on all three surfaces) |
| `accent`, `accent-hi`, `accent-lo`, `on-accent` | FICSIT orange: primary buttons, the active state, title rules, focus rings; its hover and pressed shades; text on orange |
| `conflict`, `free`, `power` | Errors and conflicts (also the danger tone), done or live, power |

Fonts: `font-sans` is Barlow (400/500/600) for reading, `font-display` is Barlow Condensed (500/600/700) for titles, headings, labels and numbers, usually `uppercase tracking-wider`. Both are self-hosted through `@fontsource`.

Utilities: `chamfer` cuts the four corners of controls (buttons, fields, segments, chips), `chamfer-window` two opposite corners of windows. Both use CSS `corner-shape: bevel` and fall back to a small radius in browsers without it. Use one of them instead of `rounded`, never both (two border radii fight). `hazard` and `hazard-danger` are diagonal stripes for a thin strip (the map mode banner, the danger zone), never a fill. `focus-ring` gives a focusable element the accent ring. Spacing follows Tailwind's 4 px scale: controls are 32 px (`sm`), 40 px (`md`), 44 px (`touch`) or 56 px (`lg`) high, and `sm` grows to 44 px below 900 px (phones), so a small control is still a touch target there; panels pad 12 px, window bodies 12 to 16 px. Small print (hints, notes, a row's second line) is 12 px on wide screens and 14 px on phones.

**Components** (`src/web/components/`; use these before writing classes of your own):

- `Button`, `IconButton`, `buttonClass()` (also for links): variants `primary` (the one main action of a view), `secondary` (a raised plate), `ghost`, `danger`, `link-accent`; sizes as above.
- `Window`: a frame with a `WindowTitleBar` (orange top rule, title in capitals, optional icon, subtitle, actions and ×; `tone="danger"` for a red rule), then the content and an optional footer of buttons; named by its title; `as` is `section` (default), `aside`, `article` (the wiki's entry) or `div`. `WINDOW_FRAME` and `POPOVER` are its classes for boxes with markup of their own (the item panel, menus, the search results). `Dialog` uses the same title bar.
- `SectionHeading` (`▍ TITLE ──── end`) for a block inside a panel or window; `Panel` is a block with one; `SectionMarker` and `SECTION_HEADING` build a custom heading (the sidebar's fold buttons).
- `StatList` with `StatRow`: label left (with an optional picture and a second line), value and unit right in tabular figures, as a `dl`; for machine numbers, totals and results. A long value (a sentence, a list of names) wraps within two thirds of the row. Tones `accent`, `danger`, `success`, `muted`. `StatTile` (in a `dl` grid, with `TileValue` for a smaller unit) is a big figure on a plate for the one to three numbers that answer a tool's question; `main` puts the answer in the accent (the planner's power, the calculator's stacks per minute).
- `Badge` (`badgeClass()`) for small labels: a role, a tier, a state, a count. Tones `neutral`, `accent`, `success`, `danger`, `power`.
- `NumberField`: a labelled `type="number"` input with its unit inside the box; screen readers hear the unit as its description, then the hint. `boxClassName` sets the width of the box alone, so a long label or hint keeps the whole width. `fieldClass()` styles any other input or select; checkboxes and radios get the accent from the base styles. Both use 16 px text below 900 px (iOS zooms into a focused control with smaller text).
- `Fold`: a block folded away until asked (a native `details`), its summary in the section heading look with the values in effect after the title (they move under it when there is no room) and an inset focus ring; for rarely changed settings. Inside a window it takes a top rule, on its own `WINDOW_FRAME`.
- `usePageBack({ to, label } | null)` (`PageActions.tsx`): a back control above a world page that leads somewhere inside the page (a world page has no header of its own; its actions go in its windows' title bars).
- `SegmentedControl` (a radio group as segments, 44 px below 900 px), `LanguageSwitch`, `ReadonlyCopyField`, `Toast`, `ConfirmDialog`, `Footer` (world list, profile page and sign-in page only), `Header`.
- `icons.tsx`: the app's 16 px line icons in `currentColor` (close, chevron, back, search, sliders, sidebar, upload, gear, collectibles (a sparkle), cave, height (contour lines, so it differs from the cave's mountain), map, ore, machine, flow, truck, pin, check, plus, fit) and the `BrandMark`. A tool passes one as `icon` (`createElement(CaveIcon)` in a `.ts` module). Pictures of items, machines and vehicles come from `GameIcon` (`features/machineWiki/icons.tsx`).

## Save import

1. The user picks a save. In Chromium browsers the save folder can be chosen once (File System Access API) and is remembered; other browsers use a normal file input.
2. The file goes to `src/web/save.worker.ts` as a transferable `ArrayBuffer`. The worker parses it with `@etothepii/satisfactory-file-parser` and reports progress.
3. `src/shared/extract.ts` collects the names of collected or destroyed actors and looted drop pods, maps aliases (Mercer Shrine to Mercer Sphere) and keeps only names that exist in the dataset.
4. The UI shows a preview: how many items will be checked and how many conflicts arise.
5. The client sends `POST /api/worlds/:id/import` with the file name, session name, save time, build, the list of names and the save's resource node data (`resourceNodes`: per node the resource class and purity the save sets, the randomisation settings, and `extractors`: per extractor on a node the node name, building kind, clock speed and Power Shards; `src/shared/resourceNodes.ts`). The save itself never leaves the browser.
6. In one transaction the server replaces the world's resource node overrides and extractors (when sent), flags every existing mark as a possible conflict, then inserts the missing marks from the save and clears the flag on marks the save confirms. Marks the save does not confirm stay checked but flagged. It bumps `rev` and broadcasts `import`.
7. If the parse result has a factory snapshot (`result.factory`), the client uploads it after the import succeeded (see "Factory snapshots"); a failed upload leaves the import as it is and shows a toast.
8. Members resolve conflicts per item or in bulk ("Trust current data" / "Trust the save"). Bulk actions only touch rows that are still flagged, so a teammate's manual change in the meantime is not overwritten. Undo restores the previous rows.

## Factory snapshots

The factory map steps through a world's saves on a timeline. Each save's factory is a `FactorySnapshot` (`src/shared/factory/snapshot.ts`: buildings with productivity, lightweight parts, belts and pipes, power lines, roads, stations and vehicles with what they hold (`cargo`, optional, added to format 1 later), markers, crates, the explored area; no player names or positions), extracted from the save in the browser by the save worker.

**Connections** (`src/shared/factory/connections.ts`, called by `extractFactory`; optional fields `links` and `circuits`, added to format 1 later, missing in older snapshots). Every port is a save component `<building>.<port>` whose `mConnectedComponent` names the other end (both ends store it). Belts: from each output port of a building (`Output*`; a lift splitter's `TopConnection`/`BottomConnection` by the lift end it meets) along belts and lifts (`ConveyorAny0` in, `ConveyorAny1` out) to the next building's port: one `SnapshotLink` with the belts and lifts upstream first (`via`), the slowest class by the Mk number in its name (the save worker has no rates), and the items lying on them (`FGConveyorChainActor*`: each belt's or lift's stretch of the chain and the items' positions). Supports (`SnapOnly0`), loose belts and ends that are not buildings of the snapshot are left out. Pipes: from each fluid port along pipelines to the next building, each pair once. Pipes have no direction in the save: a link starts at a producing port (`PipeOutputFactory*`, an extractor's `FGPipeConnectionFactory`, a pump's or valve's `Connection1`) and ends at a consuming one (`PipeInputFactory*`, a generator's port, a pump's or valve's `Connection0`); between junctions and fluid buffers it runs from the end nearer to a producer (hops through the pipe graph) to the farther, then from the end farther from a consumer. `fluid` from `FGPipeNetwork.mFluidDescriptor` of the port's `mPipeNetworkID` (only some networks store one). Pumps, valves, junctions, buffers, splitters, mergers, storage, stations and sinks are buildings of their own, so they are link ends. Circuits: per `FGPowerCircuit` its id, the buildings with a power port on it (poles, wall outlets and towers left out) and a blown fuse. The Letz Fetz save of 2026-11-08 has 1,496 links (1,187 belt, 309 pipe) and one circuit of 601 buildings: +432 kB raw, +39 kB gzip (1,374 kB, 193 kB).

**Storage.** One row per save and world in `factory_snapshots` (migration 4): `session_name` and `save_time` identify the save (unique per world, so importing a save again replaces its row), `data` is the snapshot as gzip-compressed JSON, `summary` the timeline figures as JSON, `bytes` the stored size, `imported_at` and `imported_by` (user, set to null when the user is deleted). Rows go with their world. Ids use `AUTOINCREMENT` and a replaced save gets a new id, so an id never names other content. At most 2,000 snapshots per world (`MAX_SNAPSHOTS_PER_WORLD`, a safety net; the thinning keeps a world far below it), counted after thinning; one more gives 409 `limit_reached` and nothing is stored.

**Thinning** (`src/shared/factory/retention.ts`, pure: `snapshotsToThin(list, keep)` → the ids to delete; applied by `thinSnapshots` in `domain/snapshots.ts`). Old snapshots are thinned per world and per session (snapshots of different sessions are never thinned against each other). Ages are measured back from the save time of the world's newest snapshot, not from the clock, so a world nobody plays keeps its saves:

| Age (from the newest snapshot) | Kept |
| --- | --- |
| up to 2 days | every snapshot |
| over 2 days, up to 30 days | the newest per clock hour |
| over 30 days, up to 365 days | the newest per calendar day |
| over 365 days | the newest per ISO week (Monday to Sunday) |

Hours, days and weeks are UTC buckets of the save time (the server knows no player time zone; for players in Central Europe a "day" runs from 01:00 or 02:00 local time). A snapshot goes when the same session has a newer one in the same bucket of the snapshot's own tier, so each bucket keeps its newest snapshot, whichever tier that one is in; thinning again removes nothing (idempotent). Always kept: the world's newest snapshot and the snapshot of the world's last import (`last_import_meta`: session name and save time). It runs in the same transaction as every stored snapshot (`storeSnapshot`: browser upload, "Add older saves", the save watcher), so an old save whose hour, day or week already has a newer one is thinned right away (the save watcher's answer then has `snapshot: false`, `note: 'thinned'`; the browser's upload answers 201 and the list drops it on the next fetch). The hourly housekeeping (`runHourly`, `thinAllSnapshots`) thins every world too, for snapshots stored before thinning existed. Thinned snapshots bump the world's `rev` and broadcast `snapshots`, so open timelines refresh. Simulated (`test/unit/snapshotRetention.test.ts`): 30 saves a day for a year leave 1,067 snapshots when they are spread around the clock (60 + 672 hours + 335 days), 815 in a 15-hour play day; every further year adds about 52 (one per week). The import dialog's "Add older saves" says so in one line.

**API** (`src/server/http/snapshots.ts`, rules in `domain/snapshots.ts`):

- `POST /api/worlds/:id/snapshots` (owner or admin, like the save import): the snapshot JSON with `Content-Type: application/json` (the CSRF check) and `Content-Encoding: gzip`. The route lives in its own Fastify scope whose JSON parser takes the body as bytes: at most 4 MB compressed (`bodyLimit`) and 32 MB after decompression (`maxOutputLength`, against gzip bombs), both 413. The role check runs `onRequest`, before the body is read. The JSON is validated with zod (`SnapshotSchema`, mirroring the format with bounds per list; unknown keys are dropped, so a field added to the format must be added there too); a `v` newer than the server knows gives 400 with its own message. The server stores the validated snapshot re-encoded (not the client's bytes), computes the summary (`snapshotFigures`: buildings, machines = buildings with `prod`, the mean productivity of those that report one, idle = below 1 %), bumps `rev`, broadcasts `snapshots` and answers 201 with the `SnapshotSummary`. 120 uploads per hour per world and user.
- `GET /api/worlds/:id/snapshots` (members): the summaries, newest save first.
- `GET /api/worlds/:id/snapshots/:sid` (members): the stored gzip as is (`Content-Encoding: gzip`; decompressed for a client that does not accept gzip), `Cache-Control: private, max-age=31536000, immutable`.
- `DELETE /api/worlds/:id/snapshots/:sid` (owner or admin): 204, bumps `rev`, broadcasts `snapshots`.

**Client** (`features/factory/api.ts`): `useSnapshotList(worldId)` and `useSnapshot(worldId, id)` (never refetched; a snapshot of a newer `v` is an error), `uploadSnapshot(worldId, snapshot, queryClient?)` (JSON compressed with the browser's `CompressionStream`, checked against both limits before sending; the answer goes into the cached list) and `deleteSnapshot`. The `snapshots` event and every reconnect of the event stream invalidate the list. `factoryOf(result)` reads the parse result's snapshot (missing from parsers without factory extraction).

**Import.** The save import uploads the save's snapshot after the import succeeded (`uploadFactoryAfterImport`, also when a world is created from a save). "Add older saves" (`features/import/OlderSaves.tsx`, in the import dialog and the world settings; the dialog store's `mode: 'older'`) takes several `.sav` files, parses them one after another, oldest file first, with `parseSaveFile` (a fresh save worker per file, as a promise) and shows "3 of 12" with the stage and percent. It uploads only the snapshots: checks and resource nodes stay as the newest import set them. A save whose session name differs from the world's (its last import's, else its newest snapshot's) is skipped with a note and an "Add anyway" that parses it again; a save the world already has (same session name and save time, also twice in one batch) is skipped as "Already there". The limit and the rate limit stop the run; Cancel terminates the worker.

## Save watcher

A script on the player's PC or server watches the save folder and uploads every new save to one world. The server parses it the way the browser does, so the script needs only bash and curl, PowerShell, or Docker.

**Upload tokens** (`domain/uploadTokens.ts`, `http/uploadTokens.ts`, table `upload_tokens`, migration 5). A token lets a script upload saves to one world and nothing else. Format `fsm_<id>_<secret>` (`UPLOAD_TOKEN_RE` in `src/shared/saveUpload.ts`): the row id, then 32 random bytes in base64url, so it needs no quoting in a script. Only the SHA-256 of the secret is stored; the row is found by id and the secret compared with `timingSafeEqual` (an unknown id hashes and compares too). A row has `label` (1–80 characters), `any_session` (accept saves of another session than the world's), `created_by` (set null with the user; uploads are then attributed to the world's owner), `created_at`, `last_used_at` (set on every authenticated upload) and `revoked_at`. Revoking keeps the row; a revoked token never works again. Rows go with their world. At most 20 active tokens per world (`MAX_UPLOAD_TOKENS_PER_WORLD`, 409 `limit_reached`). Owner and admins, like the save import; a user's tokens are revoked when they lose admin rights or leave the world:

- `GET /api/worlds/:id/upload-tokens`: the active tokens (`UploadTokenDto`, no secret), newest first.
- `POST /api/worlds/:id/upload-tokens` `{label, anySession}`: 201 `{token, secret}`; the secret is shown this once (`Cache-Control: no-store`).
- `DELETE /api/worlds/:id/upload-tokens/:tid`: revokes it (204; 404 when not active).

**Upload** (`http/saves.ts`, rules in `domain/saveUpload.ts`). `POST /api/worlds/:id/saves` with `Authorization: Bearer <token>`, the raw `.sav` as `application/octet-stream` and optionally `X-Save-Name` (the file name, percent-encoded UTF-8; reduced to a plain name and shown as the world's last import). In this order:

1. `onRequest`, before the body is read: the token must be active and belong to `:id` (else 401 with `WWW-Authenticate: Bearer`; no cookie is looked at), the content type must be `application/octet-stream` (415). The rate limit (60/h, `SAVE_UPLOADS_PER_HOUR`) is keyed by the token's id, else the IP.
2. The body: at most 64 MB (`MAX_SAVE_UPLOAD_BYTES`, 413). The save header is read on the event loop (`parse/header.ts`, a few hundred bytes): no header, 400.
3. The plan (`planUpload`): the world's session is its last import's, else its newest snapshot's; a save of another session is 409 `session_mismatch` unless the token has `any_session`. Newer than the last import's save time (or no import yet): `import`. Else `duplicate` when the world has a snapshot of this session and save time (200 at once, no parse), otherwise `snapshot`.
4. The parse (`parse/pool.ts`): one `worker_threads` worker per save (`parse/worker.ts`: the parser, then `extractCollected` with the dataset index, `extractResourceNodes` and `extractFactory`, the same steps as the browser's `save.worker.ts`), ended afterwards, so a parsed save never stays in memory and the event loop is never blocked. One parse at a time per process; up to 4 saves wait, more get 503 `busy` with `Retry-After: 60`, as does a parse over 120 s (the worker is ended). Each worker has a 3 GB heap limit. The worker gets the dataset through `workerData`. Under tsx (dev) and vitest it loads `worker.ts` with tsx's loader, built it loads `worker.js`. A save that does not parse is 400. Tests inject a fake through `AppDeps.saveParser`.
5. Planned again (the world may have changed during the parse), then applied (`applyUpload`): `import` runs `applyImport`, the same function as `POST /import`, attributed to the token's creator, and stores the snapshot (`parseSnapshot`, `storeSnapshot`, as an upload from the browser would); `snapshot` stores only the snapshot. A snapshot that does not fit the upload format, or a world with no room left, does not fail an import (`note`: `invalid_factory`, `limit_reached`, also `no_factory`; `thinned` when the thinning removed the stored snapshot at once), but `limit_reached` fails a `snapshot` upload (409). Broadcasts `import` and `snapshots`, so open browsers update as after a browser import.

Answer (`SaveUploadResultDto`): 201 `{status: 'imported' | 'snapshot', sessionName, saveTime, newlyChecked?, conflicts?, snapshot, note?}` or 200 `{status: 'duplicate', …}`. Timing on the Letz Fetz save of 2026-11-08 (2.5 MB, 3,193 buildings): parse 1.0 s, with the extraction 1.2 s, about 2 s per request including the worker's start; the event loop stays free (lag 1 ms); the process peaks at about 520 MB RSS.

**Scripts** (`src/web/features/saveWatcher/templates/`: `ficsmap-watch.sh`, `ficsmap-watch.ps1`, `Dockerfile`, `docker-compose.yml`; `generate.ts` fills them). The generator puts every value into the script through its language's quoting (`shQuote`, `psQuote` with all of PowerShell's single quote characters, `yamlQuote` with `$$` for Compose), in one pass, so typed text never becomes code; `configProblems` refuses control characters, a malformed token or URL, poll intervals outside 5–3600 s and upload intervals outside 0–1440 min. The download: `ficsmap-watch.sh` (LF), `ficsmap-watch.ps1` (UTF-8 with BOM and CRLF, so Windows PowerShell 5.1 reads non-ASCII names), or for Docker `ficsmap-watch.zip` (`zip.ts`, stored, the script with mode 755) with the Dockerfile, the script (pointing at `/saves` and `/state`) and a Compose file that builds the image and mounts the save folder read-only. The scripts behave alike:

- Settings at the top (server, world, token, folder, session filter, poll interval, upload interval, mode `newest` | `all`, state folder); `FICSMAP_SAVE_DIR`, `FICSMAP_STATE_DIR`, `FICSMAP_POLL_SECONDS` and `FICSMAP_UPLOAD_INTERVAL_MINUTES` override them. No `eval` or `Invoke-Expression`.
- They look at `*.sav` in the folder and one level below (the account folder under `SaveGames`), skip `ServerSettings.*.sav`, and with a session filter only names starting with `<session>_`.
- They watch the folder (`inotifywait` when installed, `FileSystemWatcher`) and also check it every poll interval.
- A file counts as written once its size and time have not changed for 5 s (a file untouched for longer is taken at once).
- A state file (`~/.local/state/ficsmap/uploaded-<world>.txt`, `%LOCALAPPDATA%\ficsmap\…`, `/state` in Docker) lists the SHA-256 of every save done (stored, duplicate, refused for good: 400, 409, 413, 415, or skipped by the upload interval), so a file is uploaded once, and the times of the accepted uploads. On the first start the saves already there except the newest are recorded as done.
- `newest` uploads only the newest new save, `all` every new one, oldest first.
- **Upload interval** (`UPLOAD_INTERVAL_MINUTES` / `$UploadIntervalMinutes`, a generator setting, default 30, 0–1440, 0 = no limit; `FICSMAP_UPLOAD_INTERVAL_MINUTES` overrides it): at most one accepted upload (201: imported or added to the timeline) per interval. A save that comes in sooner waits (logged once per save); when the interval is up, the newest waiting save is uploaded. In `newest` mode the saves in between are never looked at; in `all` mode they are logged as skipped and recorded as done, so with an interval `all` uploads the newest too and differs only in the log; with 0 it uploads every new save, oldest first, as before. The loop wakes when the interval ends (not only at the next poll). Duplicates (200), refused saves (400, 409, 413, 415) and failed uploads do not count. The time of each accepted upload is appended to the state file as `last-upload <unix seconds>` (the last such line counts; a time in the future, after the clock went back, counts as now), so a restart, `--once` from cron included, keeps the limit. The server's rate limit (60 per hour and token) stays.
- Retries after 10, 30 and 90 s (network errors, 429, 5xx), then the save waits 10 minutes; a refused token (401, 403, 404) is logged and tried again after an hour.
- They send nothing but the save, its name and the token, to the configured server only, without following redirects. bash hands the token to curl through `-K -` (stdin), so it is not in the process list.
- bash: bash 4.3+, curl, sha256sum, coreutils or busybox (`stat -c`, `find -print0`, `od`); `--once` uploads once and exits; SIGTERM stops it at once. PowerShell: 5.1 and 7 (`-SkipHttpErrorCheck` on 7, `WebException` on 5.1; TLS 1.2 on 5.1); `-Once`; log in `%LOCALAPPDATA%\ficsmap\watch-<world>.log`. Docker: `alpine:3.20` with bash, curl, inotify-tools and tini.

**Settings block** (`SaveWatcherSection.tsx`, world settings, owner and admins, `order` 45): two lines on what it does; "Upload keys": the active tokens (label, "any session", created by and when, last used) with Revoke (a `ConfirmDialog`), and a form for a new one whose secret is shown once (`ReadonlyCopyField`) and filled into the generator; "Script": the platform (`SegmentedControl`), the key (a fresh one filled in, else pasted), the save folder with presets per platform (`paths.ts`, checked against the Satisfactory wiki), the session filter (the last import's session), the poll interval, the upload interval (with one line on what it does), the mode, the warning that the file holds the key, "Download"; then the commands to run it (bash `chmod +x`, PowerShell with a Task Scheduler snippet, Docker Compose and `docker run`).

## Factory efficiency

**Analysis** (`src/shared/factory/analysis.ts`, pure, `test/unit/factoryAnalysis.test.ts`). Input: a snapshot and `AnalysisData` (`recipes`: the indexed `recipes.json`; optional `machines`: `machines.json` entries by class for generator power, fuels and Somersloop slots; optional `nodes`: the world's resource nodes by name for purity; optional `buildings`: `buildings.json` for footprints). Per machine (`machineFlow`, a building with `prod`): `kind` (manufacturer with a known recipe, extractor, generator, other); nominal output per item = product amount × 60 / duration × clock × Somersloop boost (1 + loops / slots), for extractors their rate × node purity (`PURITY_FACTOR`, the purity is kept as `purity`) × clock (the water extractor without a node, a resource well extractor at its pressurizer's clock); actual = nominal × productivity; lost = nominal − actual. A machine without a measurement counts 100 % if it was producing, else 0 % (`measured: false`). Generators get MW only (`powerProduction` × clock; geothermal its average × purity). Reasons (`REASONS`, first = main): `paused`, `noPower`, `noRecipe`, `noFuel`, `starved` (shortage), `blocked` (backs up), `surplus`, `unknown`, from the snapshot's issues; below 99 % without one an extractor is `blocked` (it has no inputs), anything else `unknown` ("runs intermittently"); an extractor whose only reason is `blocked` is `surplus` (it makes more than is taken off). Bands (`bandOf`): idle < 1 %, part load < 90 %, high < 99 %, full; `state` is the band or `paused` (`STATES`). One counting rule for the page and the map: a machine counts for every reason it has; paused machines are no band, not inefficient and their output is no loss; `isInefficient`: not paused, not only `surplus`, and below 90 % or with an issue. Hints (`hints`): with the snapshot's splines and the belt rates of `recipes.json`, each miner's output belt is the belt start or lift nearest (within 10 m) to the middle of its footprint's farthest edge (`outputPoint`, `beltAt`): `beltLimits` (the belt carries less than its nominal rate), `beltBehind` (its actual rate matches a slower belt tier), `noBelt`; for any machine `overclockUseless` (it makes no more than at 100 % although it has Power Shards: "brings nothing now"); `beltBehind` is dropped when what it makes backs up at its consumers (they take no more). With the snapshot's `links` a starved machine says what it lacks (`starvedFor`: a recipe with one ingredient that one, with several those no input belt carries any of; missing when unknown, `starvesFor(m, item)` then counts it for each). `analyzeFactory` adds per item (`items`: nominal, actual, lost, `share` lost, `status` shortage / jam / surplus / other from the main reason by lost output, its machines most loss first, loss per reason, `consumers` (machines using it: recipe ingredient, generator fuel or water) and `loadedAt` (loading stations holding it); ordered by `compareItems`: shortages first, surplus last, the rest by share lost), `consumers` per item, per class (`classes`: count, plain mean productivity, bands, paused, reasons, inefficient) and `totals` (machines, the mean productivity as `snapshotFigures` computes it for the timeline, bands, paused, reasons, generator MW produced and capacity). `itemCause(analysis, item, ctx?)` explains an item across the chain: its consumers grouped by recipe with their reasons, `transportLimited` (its makers back up while users starve for this very item, in the same production line when `ctx.lineOf` is given), and, following consumers that back up to what they make, where the jam ends (`jamEnds`, `JamEndWhy`: `noConsumer`; users starve for it: the belt or pipe to them is full `capacity`, carries under 10 % while the save tells they lack it `connection`, else `transport`, all read from the lines through `ctx.supply` (`causeContext` in `lines.ts`); `vehicles` (it waits at loading stations); or `demand`, the consumers need no more). `filterMachines` filters by class, item, reason, band, state. `diffFactory(before, after)` compares two snapshots of a world (building ids are stable across its saves; checked on three saves each of two worlds: the same id always had the same class and position; a rebuilt building gets a new id): added and removed ids, built and torn down per class, machines worse or better by at least 5 points, items whose loss changed, totals delta (power: capacity). `analyzeRoutes(snapshot, stackSizes?)` reads the stations' own tracking: per station and vehicle items per minute = items per dock / seconds between docks × 60, summed per station, the time between two docks of any vehicle (1 / Σ 1 / interval), what lies in it (`cargo`), how full its vehicles are (`fill`, the mean of the visits that tell, 0 when vehicles move nothing), `problem` (`stationProblem`, the one rule of the page's table and the map's plates: no vehicle stops, vehicles stop and move nothing, or hardly anything moves: under 1 item per minute, or holds under 5 % full while it moves under 10 per minute); per visit whether it is an empty leg and how full the vehicle is (items per dock / (stacks × stack size of what the vehicle holds, else the station; a mean weighted by count when the items differ)); per vehicle its stops (a station visited again carries its figures only at its first stop, `repeat`: the station tracks each vehicle once), its cargo and slots, empty legs, items loaded and unloaded per minute (each station once) and the round trip ≈ the time between docks × the visits on the route, averaged over its stations.

**Production lines** (`src/shared/factory/lines.ts`, pure, `test/unit/factoryLines.test.ts`; `features/factory/useLines.ts`: `useProductionLines`, built once per analysis for all sections). `buildLines(snapshot, analysis, data)` groups the machines along `links` (power is ignored); a snapshot without links has no lines. Lines: the connected parts of the link graph. Stations, sinks, Dimensional Depot uploaders and the Space Elevator are always boundaries (items leave or enter the belts there): they join no two lines, belong to every line they touch (an end in one, a start in the next) and the index maps them to the line that feeds them most, else the one they feed. A part with more than `SPLIT_ABOVE` (40) machines is cut once more at its storage containers the same way (fluid buffers stay inside: they are inline buffers). Parts without a machine are no line. A line's id is its most downstream machine (highest stage, then most output). Groups: splitters linked to each other become one `splitter` group (a manifold), likewise mergers and pipe junctions; every other logistics building is a group of its own (`logistics: true`, `kind`; cls the members' class, else the kind; productivity 1, state `full`, no band). Stages: the longest path in groups from a group without inputs, on the graph with loops cut where a depth-first search from the sources meets them (`layer`); machines with the same class and recipe (extractors: resource) on the same stage are one group ("4× Constructor"). Flows, estimated from the analysis's measured rates: producers put out their actual rate, consumers take their actual input (ingredients × clock × productivity; generators the fuel seen on their input, else their first, and water). In topological order each building hands its supply (a machine its outputs, a logistics building what came in) to its outgoing links that can carry the item (belt solid, pipe fluid; not a pipe of another fluid or a belt with only other items on it): first evenly up to the needs of the consumers behind each link (water-filling), the rest evenly to links leading to storage, stations or sinks, and what is still left goes on evenly by room (a machine's measured output did leave it; a splitter, merger, junction, pump or valve passes on what came in, so in = out); never more than a belt's or pipe's capacity (only that is dropped); links that close a loop carry nothing (a building with a way back into a loop keeps its rest there). A machine fed by several links asks each for a share of its need: evenly first, then in three more rounds by what each brought. A building with no inputs in the line (storage, an unloading station) delivers what is taken. Edges aggregate the links between two groups (internal links of a manifold are left out; the line's `via` lists every belt, lift and pipe, and the index maps them to the line too): flow (the main item, all items when several), capacity (the dataset's belt or pipeline rate of the slowest class, summed; `perLink` when all links have the same one, `pipe` for pipes), saturated at ≥ 95 %, `exact` when saturated but nothing before it backs up (it carries exactly what is made: "full, just enough", no fault). Products: what flows into storage, stations or sinks plus outputs with no link at all; inputs: what comes out of storage or stations; `actual` sums the solid products (else the fluid ones), `nominal` their makers' nominal output in the share that leaves the line; `productivity` the plain mean of its measured machines. Bottleneck, by the same rules as the item chain: (1) an edge between makers of its item that back up and machines after it (through logistics) that starve for that item or run intermittently: full (`capacity`), or under 10 % while the save tells they lack it (`connection`); the one with the most loss behind it. (2) Else the machine group losing the most machine-equivalents (Σ 1 − productivity, paused and surplus-only members left out, at least 0.05) with its main reason; backing up, the jam is followed downstream to the next group losing most as long as that one loses at least a quarter of where it started (else `demand` where it ends: copper sheet, not the circuit board that lacks plastic); starved, it names the input it lacks most (`short`: what arrives and what it needs at its clock speed, its makers in the line, their mean productivity, extractors or not) and moves upstream to a maker that starves itself. Extractor hints from the line (`ProductionLines.hints`, `LineHint`, shown with `mergeHints`, which drops `beltBehind` then): the first full edge after a merger or splitter before any machine is `sharedBeltFull` for the extractors that back up, `beltExact` for those that do not. One reading for the page and the map: `lineHasIssue` (one `PROBLEMS` set: capacity, connection, no power, no recipe, no fuel, starved, blocked), `lineLoss` (lost machine-equivalents), `sortLines` (problems first, then by loss, then machines). `causeContext(lines, analysis)` gives `itemCause` the lines; `stationConsumers(lines, analysis, data, station, items)` the machines behind an unloading station that use what it brings and how many starve for it. `npm run inspect-factory -- <save> --data data/<version>` prints the lines (`--line <id>` one in detail, `--lines out.json` writes them). It also lists the lines as the page reads them (`--lang de|en`: order, name, issue, bottleneck sentence). Checked on the Letz Fetz save of 2026-11-08: 13 lines with 354 of 358 machines (the rest has no belt), 38 ms; the miners' first belts match the page's belt hints (30 of 30); the copper chain runs from 16 smelters to Wire and Copper Sheet, its wire through a storage container (a cut) to the Cable constructors of the next line.

**Shared state for the factory page and the factory map.** `features/factory/view.ts` (`useFactoryView`): `selectedId` (null = the newest save), `compareId` (null = no comparison), `highlight` (building, station or vehicle ids of the selected snapshot) with `highlightSeq` (bumped by every `showOnMap(ids)`, so the map fits again), `select`, `compareWith`, `showOnMap`, `clearHighlight`, `reset`. `timeline.ts`: `resolveTimeline(list, selectedId, compareId)` (oldest first; the selected one, falling back to the newest; the compared one, never the selected), `stepId`, `defaultCompareId` (the save before, else after), `useTimeline(worldId)` (the list resolved against the store) and `useFactoryWorld(worldId)` (resets the view when another world is entered); the page's own filters, sort and unfolded rows are `useFactoryPage`. `data.ts`: `useFactoryData(version, worldId)` (recipes, machines, buildings and the world's nodes as `AnalysisData`, plus `FactoryLabels`: building and item names in both languages from `buildings.json`, `machines.json`, `recipes.json`, else the class name made readable, and the building's picture class), `useSnapshotAnalysis(worldId, id, data)` (snapshot, analysis, routes; memoised per snapshot), `useFactoryDiff(before, after)`, `useBuildings(version)`.

Logistics nodes are half-height chips on a rail through their row. "Machines only" also leaves out storage and stations at an end whose belts carry next to nothing (`IDLE_FLOW`). Wider than its panel, the diagram opens at the bottleneck (`FlowDiagram`'s `focus`, also panned into view along the flow), never with a node cut at the left, with a "more →" chip while it continues; it pans and zooms like the planner's and has its own direction switch (logistics chips then sit on a rail across their column). A snapshot without `links` (imported before connections were read) says so with "Import save again" for the owner and admins.

## Factory map

The `factoryMap` feature (`features/factory/map/`) draws a world's saved factory on the map as a 2D sketch from above, with a timeline through its snapshots and the changes between two of them. It shares the snapshot choice, the comparison and the highlight with the factory page (`useFactoryView`), and reads the page's timeline (`useTimeline`), analysis (`useFactoryData`, `useSnapshotAnalysis`, `useFactoryDiff`), bands, reasons and their icons, so both say the same. Its own state is `useFactoryMap` (remembered per device under `ficsmap:factoryMap`, version 2: the switch, the layers, the colour mode (productivity by default; a version 1 colour mode is ignored, it was stored on every change while "category" was the default), whether "Changes" follows the save before or a chosen one; not remembered: the selection, where the focus returns when the info window closes, and the last fitted highlight).

**Parts.** A switch in the map's tools ("Factory plan", `order` 32; distinct from the page's "Factory" tab), the sidebar panel "Factory plan" (`FactoryPanel`: the switch; without snapshots the empty state with "Import save" and, for the owner and admins, "Add older saves", the import dialog's two modes; switching the plan on gives this panel the room (`usePanelsCollapsed.setSolo`: the other sidebar panels show folded and it scrolls into view, without touching what is remembered; switching off hands every panel the user did not touch meanwhile back as it was); the colour mode as a `SegmentedControl`; the legend with counts, in the productivity mode the bands and reasons as buttons that call `showOnMap` with those machines; the layers as checkboxes; stations and vehicles in a `Fold`, a click selects and shows one), the map layer `FactoryMapLayer`, and three map overlays: the timeline (`Timeline.tsx`), the marking chip (`HighlightChip.tsx`: "6 buildings marked" with a 44 px × that clears it, a polite live region) and the info window (`FactoryInfo.tsx`). Everything that loads data is mounted only while the switch is on, so the map costs nothing otherwise. `mapData.ts` (`useMapData`) combines the shown snapshot, its scene and analysis, the compared snapshot and the diffs; the shown scene stays (drawn faded) while the next snapshot downloads, and the neighbours of the shown save are prefetched.

**Scene** (`scene.ts`, pure). A snapshot becomes a `Scene` once per snapshot, `buildings.json` index, bounds and analysis (`sceneOf`, a WeakMap cache): every position in map units (the 256-unit zoom-0 image of CRS.Simple, x east, y south; one unit is about 29 m in 1.2), each building's outline (`footprintRect`) and body boxes (`splitBoxes`: the boxes without `soft`, else all) as rotated corners (`rectCorners`: yaw 0 = +x, positive turns +x towards +y), its map kind, band and reasons (the analysis's, else `reasonsOf` from the save alone), floor pieces (lightweight buildables and actor structures; footprint, else grid size, else 8 m) lowest first, lines (`lineStyle`: belts Mk.1–6, pipes Mk.1/2, hypertubes, roads, rails) as flat point arrays, power lines, stations and vehicles with the page's `analyzeRoutes` figures, markers, crates, and a 0.5-unit grid for hit tests. `pickBuilding` takes the building drawn on top at a point: machines before other buildings before logistics parts, then the smallest.

**Drawing** (`FactoryCanvasLayer.ts`): one canvas in the pane `ficsmap-factory` (z-index 410: above the tiles, the explored-area veil at 300 and the cave areas at 350, below the cave entrances at 420, the collectible markers at 450, the resource nodes at 455 and the vehicle route at 460). The geometry is grouped per 4-unit chunk into `Path2D`s in map units (floor; building bodies per fill key for both colour modes; soft boxes; lines per kind and tier; power lines), built once per scene; a frame culls the chunks to the view and fills or strokes each group under one transform, so panning costs little more than the fills. Per-building detail (pictures, names, reason glyphs) loops only over the visible chunks. It redraws (one frame at most) on move and zoom and scales like the tiles during a zoom animation, like the other canvas layers. Pictures are the dataset's item icons (`pictures.ts`, loaded once per URL, the canvas redraws when one arrives).

**Levels of detail** (`lod.ts`). Below zoom 4 machines are dots and the floor plan shows as areas: in the category mode 3 px squares, in the productivity mode a shape per band (stopped a red ×, part load a diamond, nearly full a small square, full and paused a tiny dot), problems on top; from 4 buildings are their boxes, belts and pipes show; from 5 outlines and power lines (when on); from 6 station plates and vehicle names; from 7 station plates carry the station's number ("Nr. 4", `stationNumber`, counted as the Fabrik page names "Lkw-Station 4"); from 8 (`closeUp`) the band hatching and tint drop to 35 % and a problem machine's status is its 3 px border in the band colour and its glyph, the lower floor of a stack (`SceneBuilding.under`: a building of about its size at least 2.5 m higher right above it; `pickBuilding` takes the upper one) is drawn inset and dimmed under it and only the upper floor gets picture, name and glyphs; also from 8 the soft boxes, the vehicles' real outline and on machines the picture of the item they make (`SceneBuilding.product`, the analysis's first output: the recipe's main product, an extractor's resource) in colour, pinned to the tile's lower right corner like the planner's nodes. A building shows the game picture, in greys at 60 % (`greyPicture`), and its name (cut to fit) once its shorter side is 64 px; belt and pipe attachments, poles and signs never get a name and their picture only at zoom 10. Stations show their symbol and plate instead of picture and name. Lines widen from zoom 7. The map's max zoom is 7 (`map/zoom.ts`, `BASE_MAX_ZOOM`); while the factory layers are on they ask for 10 (`requestDetailZoom`, also before the map is created when the switch is remembered as on, so a close-up view is kept), the tiles are scaled beyond their native zoom 5.

**Colours** (`theme.css`, `style.ts`). Category mode: three hues for the machines, `fac-production` (blue), `fac-extraction` (teal), `fac-power` (amber), picked from the data-viz reference palette's dark steps and validated as a set (all pairs: protan/deutan ΔE ≥ 8.4, normal vision ≥ 19.8, each ≥ 3:1 on `bg`); `fac-building` and `fac-minor`, two neutrals, for storage, stations and other buildings and for logistics parts; `fac-floor` with `fac-floor-edge` for the floor plan; `fac-belt` (wider and brighter per tier), `fac-pipe`, `fac-road`. From zoom 5 the category mode is a blueprint: bodies at 75 % with a crisp 1 px edge in the fill lightened. Productivity mode (the default): the page's band colours (`BAND_TOKEN`, as `BAND_FILL`: stopped `conflict`, part load `accent`, nearly full `power`, full `free`), drawn by `BAND_LOOK` so problems pop and healthy machines recede, each band with a cue besides its colour: full a faint tint (20 %) with an edge in the band colour, nearly full a stronger tint with sparse dots, part load diagonal stripes, stopped solid with a lighter cross-hatch; paused machines (`SceneBuilding.paused`, the analysis's own state) neutral `edge` (the page's `STATE_FILL.paused`) with the pause glyph; buildings without production `fac-minor` at 30 %. Problems are drawn on top (`rank`); a band or reason added to the analysis later falls back to a neutral look and a ring without glyph. Reason glyphs (the page's `REASON_PATHS` as `Path2D` in a dark disk ringed in the band colour) show only in the productivity mode, on buildings at least 18 px across. The legend's swatches (`BandSwatch`) are drawn the same way; its counts are the page's (`totals.bands`, `totals.paused`, `totals.reasons`, where a machine counts for each of its reasons; "Paused" is a state row, not repeated among the reasons), the ids behind each row come from the scene. The base hues are the page's status tokens; the tile tints are not told apart by colour alone (nearly full vs part load ΔE 5 in normal vision), which is what the patterns and dot shapes are for. The highlight is the text colour `fg` with a soft glow and a dark casing (at least about 18 px around small buildings), pulsing once where the map lands (`PULSE_MS`, not with reduced motion); the selection and the selected vehicle's route are `fg` on a dark casing, not the accent.

**Layers** (`FACTORY_LAYERS`): floor plan, buildings, belts and pipes, power lines (off by default), roads with stations and vehicles, map markers, crates, explored area (off by default: the save's fog PNG turned into a veil of `bg` over unexplored ground, `fogVeil`, an image overlay in the pane `ficsmap-factory-fog`). Stations are a plate with an arrow up (loading) or down (unloading), ringed white when in use, red when vehicles dock but move nothing, dashed when none docks; their label is "↑ 312 /min · 80 %" (how full its vehicles are, the page's `StationVisit.fill`; the player's name first when it has one) after the picture of what lies in the station (`StationFlow.cargo`); a problem station (`StationFlow.problem`: no vehicles, or nothing moved) has a red ring and a red line; one that moves hardly anything (`lowThroughput`) a ring and line in the accent, a warning (`SceneStation.low`; its route legs stay neutral). The scene takes the page's route analysis (`SnapshotAnalysis.routes`, with stack sizes) when there is one. Stations closer than 40 px share one plate (loading lines first, then unloading). Labels are 13 px (14 px on coarse pointers) and never cover each other: a greedy pass places the selected vehicle's name first, then the station plates, vehicle names (right of the arrow, else left) and marker names, and skips what would collide. Vehicles are an arrow along their heading (vehicle green with autopilot, grey without). A selected vehicle's route follows the roads: `routePath` (`routes.ts`) joins road segments at their end points, finds the shortest way between consecutive stops (back to the first) and falls back to the straight line; its stops get numbered badges. `vehicleRoute` marks the stops where the vehicle moves nothing (0 /min) or whose station is out of use (`StationFlow.problem` no vehicles or nothing moved; not `lowThroughput`), the legs into them and the legs out of problem stations: those legs and badges are drawn in `conflict`.

**Interaction.** Hover is the mouse's only (pointer events with `pointerType` `mouse`; a touch never leaves a tip behind) and ends when the pointer leaves the map's container (the overlays lie beside it, so entering the info window counts), over a map control, and when the selection or the line changes. It shows a tooltip right of the pointed building's cluster (the line's buildings within 220 px), else left of it (name; for machines productivity and reasons; for stations items per minute); a click in the inspect mode selects a building, station or vehicle (a collectible marker drawn above takes its own clicks; selecting one closes the other's box), Esc (`escapeClosesInfo`: not when handled already, nor from a field or a dialog) or × clears it. The info window is a `Window` over the right of the map like the item panel (the zoom keys move to its left; on phones a sheet above the bottom sheet's peek, and the timeline hides meanwhile); after a selection the map pans the building clear of the window (`panInside`, padded by the window's size; not right after a fit). A machine: the productivity bar, then per output "actual of target" with the loss, then its state (`stateKey`), reasons as `ReasonBadge`s, the page's hints (belt limits, no belt, overclocking that brings nothing), the node's purity, the belt at its output, recipe, clock speed, Power Shards, Somersloops, power (the page's `machineFlow`); a station ("Station"): mode, items per minute, the time between docks of any vehicle (`combinedInterval`), what lies in it, its problem in red and its vehicles (full name, figures and fill on a second line; each selects the vehicle); a vehicle: autopilot, fuel, what it loads and unloads, the estimated round trip, what it holds (station and vehicle cargo: picture, name cut to fit and count on one line, right-aligned; past four items "+n more" shows the rest), its empty legs and its route (each stop selects the station; 0 /min in `conflict`). List buttons are at least 44 px high. Opened from a button (`select(…, { focus: true, opener })`: the panel's lists, a stop, a station's vehicle) the focus moves to the window's title (`Window`'s `titleRef`) and goes back to the first opener when it closes. With changes marked it says "New since …" or the productivity before. `showOnMap(ids)` (the page's "On the map", the panel's legend): the map switches the layers on, turns to the productivity mode when the ids hold a machine, outlines those ids, fits to them (at most zoom 8) once per `highlightSeq`, and selects a vehicle when the ids hold exactly one (a route: the vehicle and its stations), so its route shows.

**Timeline and changes** (`Timeline.tsx`): a bar at the bottom of the map (on phones above the sheet's peek and the map attribution) in the Fabrik page's design: older and newer buttons (`aria-disabled` at the ends, so the keyboard focus stays), the shown save's date (a polite live region) and "n of m", a diamond per save on the page's time axis (`axisPositions`, `labelIndices`; a radio group, filled = shown, hollow = compared), arrow keys on the bar, a loading note that stays mounted and only changes its text. On phones one row: older, the date without the year, newer, and "Changes" as an icon toggle (`aria-pressed`); no axis and no compare select. Choosing the newest save stores no id, so a later import moves on to it. "Changes" compares with the save before (`defaultCompareId`) and keeps following it while stepping; the select picks any other save, which then stays. Buildings and productivity come from the page's `diffFactory` (added and removed ids, better and worse by at least 5 points); the map adds floor pieces (by class and position) and lines (by id) itself (`diff.ts`). Unchanged buildings turn neutral grey under a light veil, so only the changes carry colour: new buildings in their colour with a green outline, removed ones red ghosts with a dashed edge where they stood, better or worse ones in their band colour with a triangle up or down; the bar counts them in the Fabrik page's rows (`diffSummary` in `changes.ts`: machines, logistics with the belts, pipes and roads, foundations with the floor pieces, "other" only when present), then better and worse, and "Go to the changes" steps through the areas of changes (`changeAreas`: the densest 6-unit cell with its eight neighbours, its changes taken out, again until none are left), densest first: the button then reads "Area 1 of n ›". Foundations, walls and ramps are counted in the bar but not tinted.

**Production lines** (`lineView.ts`, `LinesSection.tsx`, `LineCard.tsx`). The shown save's lines (`buildLines`, `src/shared/factory/lines.ts`, built once per snapshot by `mapData.ts`'s `linesOf`) light up on the map: pointing at a building of a line, at one of its belts or pipes (`pickLineSpline`, 5 px, from zoom 4), or at a row of the panel's list (or focusing it) shows that line, else the chosen one (`useFactoryView.lineId`, shared with the Fabrik page's line diagram; the pointed one is `useFactoryMap.hoverLineId`, map only). The canvas (`drawLine`) lays a `bg` veil over the factory with the line's building bodies cut out (even-odd), outlines its buildings (rings around the machines' dots zoomed out), and draws each connection's belts and pipes (`LineEdge.via`, oriented along the flow by `lineGeometry`: a belt's spline runs the way its items move, a pipe is turned to start at the upstream group) bold on a dark casing in the colour of its load (flow per minute over the slowest belt's capacity, `edgeLoad`: below 50 % `muted`, busy `fg`, from 95 % full in `power` and wider with a two-bar glyph, the line's bottleneck in `conflict`, widest, with "!"), with chevrons in the flow direction from zoom 5; the line's other belts and pipes (`ProductionLine.via` inside groups, a manifold's belts) thin in `muted`; the geometry and its paths are built once per scene and line. The hover tip names the building's line. A building in several lines (a station, a sink at a boundary) counts for the chosen line when it is part of it (`lineOf(…, prefer)`), else for the line the index names. A click (tap) on a building or belt of another line chooses that line, a click within the chosen line opens the building (with a way back to the line's card), a click on empty ground closes a building but keeps the line; Esc steps back (building, then line), × closes both. The info window's line card (on phones a peek of at most 32 % of the map's height, `PEEK_SHARE`, with mean productivity, bottleneck and "Als Diagramm"; a tap or an upward drag on its title bar, its chevron or "Show details" unfolds it; the timeline hides meanwhile): mean productivity, the bottleneck in words (led by the page's "Engpass" chip, `BottleneckChip`, when `lineHasIssue`, else a muted "Grenze:"; the panel's list marks problem lines with the same chip) ("Förderband Mk.1 voll zwischen Schmelzofen und Konstruktor", "Konstruktor: Mangel"), actual of nominal output, the machines by class as buttons (each `showOnMap` with those machines of the line, the keyboard's way to them), products and what is supplied from outside, "Als Diagramm" (`linePath`, the Fabrik page's line diagram on this line) and "Zum Strang" (fit the map to it). A line chosen by a click on the map keeps the building or belt clicked as `lineAnchor`: the map pans it clear of the card (as for a selection), so a second tap reaches it. The panel's fold "Produktionsstränge" lists the lines with a problem first (`lineHasIssue`: a full connection, or a group held back by something other than missing demand or surplus), then by machines; each row the products' pictures, name, machines and the mean productivity as a bar; 10 rows, then "Show all". A snapshot without `links` (imported before connections were read) says so, with the import button for the owner and admins. ## Dataset

The dataset is static and versioned by game version: `<DATASET_DIR>/<game-version>/` with `collectibles.min.json`, `map.json`, `biomes.geojson`, `crash-sites.json`, `tiles/{z}/{x}/{y}.webp`, `icons/` and optionally `caves.geojson`, `machines.json` (the machine and vehicle wiki, from the game's `CommunityResources/Docs` files via `--docs`), `icons/items/` (the game's pictures of items, machines and vehicles for the wiki: `index.json` with the sizes and classes, `<size>/<descriptor class>.webp` at 64 and 256 px; the browser loads the index when the wiki opens or the resource node layer or panel shows, and requests only listed pictures, in the size that fits the screen via `srcset`; without it the wiki shows no pictures), `recipes.json` (production planner, fetched when the planner opens; also the extraction rates of the resource node layer and panel, and for the factory page the items' stack sizes, the belt and lift rates and the pipelines' flow limits (`pipes`: `mFlowLimit` m³/s × 60, Mk.1 300, Mk.2 600 m³/min)), `transport.json` (vehicle calculator), `buildings.json` (factory map: every buildable and vehicle class with names, category, footprint and picture; see `src/shared/buildings.ts`) and `height/` (`meta.json` plus 500 m tiles `<ti>_<tj>.bin.gz`, fetched by the browser on hover and unpacked with `DecompressionStream`; tile URLs carry the content hash from `meta.json` because non-JSON files are served as immutable) and `resource-nodes.json` (`{version, resources: [{id, name}], nodes: [name, kind, resource, purity, x, y, z, core?]}`; kind `node`, `geyser`, `core` or `satellite`, purity `impure`/`normal`/`pure`, null for cores; geysers have the pseudo resource `Geyser`; loaded only by the browser). It is not in the repository and not in the Docker image; it is mounted at run time. The server loads `collectibles.min.json` at start and serves the directory under `/data/`.

`npm run dataset` (`scripts/build-dataset.ts`) builds it from:

- the output of SatisfactoryTools/AssetsExtractor `world-extractor-net` with the patch in `data-src/extractor/` (resource nodes from its `--out` file `default-world.json`, collectibles, drop-pod requirements, Mercer shrines, cave volumes and the 3D geometry around each cave, the height grid, the map area raster, tiles, icons; see `data-src/extractor/README.md`),
- a `--data-src` folder with crash-site data and the hand-drawn biome polygons with their calibration (used only when the extractor output has no `map-areas/`),
- optionally `--docs`, the game's `CommunityResources/Docs` folder (default `<extractor>/docs`), for `recipes.json` (`scripts/recipes.ts`; see `data-src/extractor/README.md`, "Recipes and buildings") and, with the extractor's `transport.json`, `transport.json` (`scripts/transport.ts`),
- the extractor's descriptor pictures (`--icons-out`, default `<extractor>/icons`) for `icons/items/` (`scripts/icons.ts`): every item, resource, equipment and vehicle picture, those of the buildings that are wiki entries (the Docs say which) and, when the extractor's `buildings-raw.json` is there, those of every building class in `buildings.json` (in 1.2.5.0 all 747),
- the extractor's buildables (`--buildings-out`, default `<extractor>/buildings-raw.json`) with the Docs for `buildings.json` (`scripts/buildings.ts`; see `data-src/extractor/README.md`, "Buildings").

The build filters to the registry types, assigns each item a biome and a number within it, adds drop-pod requirements and shrine aliases, and fails on missing types, duplicate names or items without a biome. Each world records the dataset version it was created with.

## Versioning and version guard

The version in `package.json` is the app version (SemVer, bumped by hand). `GET /api/version` returns it, and the UI shows it with a link to the GitHub release.

On start (`src/server/main.ts`, logic in `src/server/version/guard.ts`) the app compares its version with the one stored in `ficsmap-version.json` next to the database:

- **Same version:** start normally.
- **Newer version:** back up the database to `backups/pre-v<new>-from-v<old>-<timestamp>.db`, run migrations, start, store the new version.
- **Older version (rollback):** do not touch the database. Start a separate maintenance app (`version/maintenance.ts`), where every page shows a notice. An owner confirms in the browser, or an operator runs the `rollback` command in the container (`version/cli.ts`, `docker compose run --rm ficsmap rollback [--yes]`). The current database is saved as `backups/pre-rollback-v<from>-to-v<to>-<timestamp>.db`, the pre-upgrade backup is restored, and the process exits so the container restarts into the old version. Without a matching backup the rollback is refused if the schema (`user_version`) is newer than the old version supports; otherwise it continues without a restore.

## Scaling limits

ficsmap is built for one instance per database:

- The SSE hub is in memory. Events are only delivered to clients connected to the same process.
- Rate limits are in memory and per process.
- SQLite has a single writer.

Running several containers against the same database is not supported. For the intended use (groups of friends, a few dozen users) one instance is plenty.

## Tests

Vitest with three groups: `test/unit` (pure logic and domain), `test/api` (the Fastify app with an in-memory database and a fake Discord client) and `test/web` (React components with Testing Library and jsdom). Tests that need the real dataset or a save file (`FICSMAP_SAVE_FIXTURE`) are skipped when it is missing.
